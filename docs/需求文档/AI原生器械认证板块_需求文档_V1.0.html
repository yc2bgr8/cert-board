1 背景与目标

1.1 公司目标

管理层对AI-native的要求是：AI在人类监督下可以完成工作过程，并且胜任工作，AI以目标为导向持续迭代优化工作。

2026年11月16日管理层进一步明确了形态：人看到的过程尽量少；在板块里和对应的AI对话；AI在后台按业务流程真正去执行；结果返回给人简单审核；具体流程人尽量少看甚至不看，由AI在对话中汇报。

2026年11月17日项目负责人进一步说明公司想要的形态：类似Claude Code、Codex这样的Agent，只是做的是我们自己的业务；板块里有不同角色的Agent。人和它对话，交代要申请什么产品的认证，Agent去做，把结果返给人；人审核没问题就可以提交（例如提交510(k)申报包），有问题就直接说，AI去改进。2026年11月18日管理层进一步确认：登录后不区分角色；首版分为注册Agent和维护Agent；过程由Agent完成，人审核最终结果；权限可以像Codex那样选择「请求批准」或「完全允许」（2.1、2.2、2.4）。

两者是一致的：Agent的工作过程可以展开查看，但人不需要看；人看的是交付物、改动和依据。

此前的方案（需求V0.4和研发流程平台）都以系统页面和台账为中心：人登录系统、维护主表、推进流程，AI在若干环节提供建议。本文改为以AI执行为中心：

1.3 板块范围与两项任务

注册流程：选定一个产品和一个市场，走完「定路径 → 规划证据 → 组织测试 → 装申报包 → 提交 → 回答审评问题 → 拿到许可」。一个510(k)、一个加拿大MDL，就是一个注册项目。

体系维护：取得许可后，公司和产品持续合法：质量体系年年能通过审核；证书、注册、列名、年费、代理人不逾期；产品、材料、供应商、标签、软件变更时，判断各市场是否需要重新申报或更新；上市后的不良事件、更正与召回在法定时限内处理；对外宣称不超出获准范围。这条线没有结束日期。

市场范围：美国FDA和加拿大卫生部（含MDSAP）为主要市场，按深度要求实现；欧盟、英国、澳大利亚、韩国、新加坡等其他市场以「市场规则包」方式扩展，需要时启用。

产品范围：覆盖两类器械：一类是L08止鼾口含器这样的无源器械；另一类是JoyBreath CPAP这样的有源器械，带软件、无线连接和网络安全要求，申报时会多出电气安全与EMC、产品专用性能标准、气路生物相容性、软件、网络安全、人因、无线共存等章节。

不在范围内：研发板块的工作（设计开发、测试执行、研发项目管理、PDM）；自动登录监管门户提交；对外签署任何声明；替代法务意见。研发等部门作为资料提供方与本板块交互（见3.7）。

以下四个场景说明本文要实现的工作方式，对话为示意。

场景一：发起一个注册目标

场景二：AI主动发现维护事项

AI：提醒：FDA企业年度注册窗口12月31日关闭，还剩44天。我核对了FDA公开数据：L08的列名企业注册到期年份显示为2027，可能已完成续期，但我没有找到年费缴纳凭证。另外，列名中有4个品牌名没有出现在510(k)资料里。需要你确认：年费是否已缴；这4个品牌是否已经过标签复核。

2 工作方式

2.1 角色

角色在本板块中的职责和AI的交互方式
注册Agent执行注册项目（R01–R12）；可以读取台账回答问题；对注册项目中任务的结果负责—
维护Agent执行维护事项（M01–M12），以及S01合规报告与证照资料包、S02 UPC、S04周报与管理层决策项；可以读取台账回答问题；对维护事项中任务的结果负责—
注册人员注册部门的成员。登录后不区分角色：每个人都可以发起和处理注册项目与维护事项，都可以审核结果。界面上只显示人名。每个注册项目和每个维护事项有一位负责人对话：下达目标、审核结果、处理批准请求
管理层只对路径、重大风险、大额费用、关键商业结论作决定不登录。经企业微信或邮件接收决策项和周报；决定由注册人员记录到对应项目
销售人员合规报告、证照资料包和UPC的业务需求方不登录。由注册人员在对话中代为提出（以后可以经邮件转入，5.7）
资料提供方研发、品质、采购、生产提供资料和事实；CRO、实验室、当地代理提供交付物接收AI的资料请求和催办，回复文件或说明；不需要登录新系统
有管理权限的人员系统维护：用户、模型配置、预算、任务监控。管理权限不是业务角色，不做法规判断在设置中看到维护页入口（NF14）

每个注册项目和每个维护事项有一位负责人：接收提醒，事项出现在负责人的「待我处理」中；负责人可以更换。其他注册人员同样可以查看和审核。需要同事复核时，在审核卡上「转交他人」。质量体系是否要求申报资料或法规判断由第二人复核，请质量负责人确认（D22）；确认需要时，再加为可配置的规则。

两个Agent：首版分为注册Agent和维护Agent。

Agent负责切片中的能力
注册Agent注册项目：R01–R12R09 申报一致性检查
维护Agent维护事项：M01–M12；S01 合规报告与证照资料包、S02 UPC（都依赖证照台账）；S04 周报与管理层决策项M02 美国注册与列名核查

规则：

  1. 两个Agent共用同一个内核、同一套工具和约束、同一套预算和计量、同一个资料库和项目工作区机制；各自有系统提示词、技能索引和评测集。
  2. 注册项目下的对话用注册Agent，维护事项下的对话用维护Agent；「新对话」由人选择，默认注册Agent。唤醒时按目标所属项目的类型选择Agent。
  3. S03（沟通与会议归档）由所属项目的Agent处理；S05（AI工作质量保障）是系统功能，不属于某个Agent。
  4. 两个Agent都可以读取台账回答问题（台账问答，5.6）。
  5. 交接：R12获证后，注册Agent建立对应的维护事项并附移交清单（按当前对话的权限模式执行），之后由维护Agent负责。
  6. 以后需要更多角色Agent时，按同样方式增加Agent定义。

需要分头调查时，两个Agent都可以调用子Agent（如一致性检查、法规检索，见6.2）。

2.2 人与AI的分工原则

  1. AI负责过程。 收集资料、检索、比对、计算期限、起草、催办、维护台账、生成文件，由Agent完成：人在线时在对话中直接做，需要等待外部的工作在后台继续。
  2. 人负责目标和最终结果。 分类与路径、对比器械、法规适用性、变更是否需申报、发补答复立场等判断，在过程中由Agent作出（请求批准模式下先提出建议、等人确认），写明理由、备选方案和依据，并在最终的审核卡中逐条列出。人不同意时在对话中说明，Agent修改后重新提交。
  3. 对外动作只能由人完成。 监管门户提交、缴费、对外签署、向监管机构或客户发出正式文件，由人完成；AI准备材料、说明步骤，并在人完成后核对回执。
  4. 管理层经企业微信或邮件收决策项。 路径、重大风险、大额费用、关键商业结论由Agent准备，经企业微信或邮件发给管理层（S04，按内部消息的规则发送）。管理层不登录；其决定由注册人员记录到对应的项目中。
  5. AI对结果负责。 AI交付的每个结果都要附依据、自检结果和不确定事项；做不到的要明确说「未完成」及原因，不能用一段通顺的回复掩盖失败。
  6. 缺信息就问，不猜测、不编造。 资料中没有的信息（如收件人、日期、编号），AI交还给人补充，不能填写推测值或占位内容后继续执行（RV-02）。
  7. 边界由系统强制执行。 动作级别（2.4）、审批、预算（6.7）和数据边界（5.5）由系统强制执行，不依赖AI自觉遵守。验证中两个千问模型都主动拒绝了越权指令，但模型自觉不能作为安全保证（RV-02）。
  8. Agent在对话中汇报进度。 开始一项工作时列出步骤；每完成一步，在对话中说明做到了哪一步、下一步做什么。人不在线时，进度同样写进对话（3.3、3.5）。

全景表为每项工作设了目标等级（L1–L3），本文的等级与其对应，具体以注册人员和管理层确认为准（D07）。

晋级和降级规则：

  1. 每项能力当前的等级可以随时查询，审核卡上显示结果所属能力的等级。
  2. 晋级依据评测和试点数据：某项能力在评测集（第8章）和试点中连续达到约定的通过率、且无严重错误时，由AI提出晋级申请，附评测报告；管理层批准后生效。参考项目只有人工设置的模式，没有等级和晋级机制，这部分需要我们自行设计（调研3.16）。
  3. 降级自动触发：出现严重错误或连续退回时，自动降一级，并在复盘中说明原因。
  4. 等级只决定「人审核多少」，不改变动作级别（2.4）的限制。法规判断、对外动作、风险接受永远不进入等级3；不可逆动作在任何等级下都只能由人执行。

首版所有能力的最终结果都交人审核（相当于等级2），包括总览表里目标等级为3的能力。等级3（抽查后直接生效）以后按评测和试用数据开放。4.1中R07、M06、S03、S04的首版等级因此记为2，目标等级仍为3。内部请求不再因达到等级3而免逐次批准，改由权限模式决定（2.4）。

  1. 结果交人审核。 交付物以审核卡提交，人通过后才算完成；定稿冻结只在人批准后发生（2.6）。
  2. 发往公司外部的消息每条都要人批准。 收件人是CRO、实验室、代理、客户等公司外部对象的，先生成外发提案，人批准后进入外发队列，发送前再检查（3.4）。
  3. 法律和质量体系效力的动作只能由人完成。 监管门户提交、缴费、签署、向监管机构或客户发正式文件由人完成；不可逆动作始终拒绝；真值字段只由人写。

  5. 批准只能在浏览器界面中点击。 在对话或企业微信中说「同意」不算批准（3.4、IX-08）。
  6. 工具目录按模式生成。 只读模式下写入工具不出现在目录中（上文规则3）。

批准请求的形式：过程中Agent要做需要先问的事时，在输入框上方出现一张小卡片，写明Agent要做什么、改哪条记录（改前和改后的值），或消息的收件人和内容。按钮为「允许」「本对话中都允许」（同一个工具在本对话内以后不再问）和「拒绝」（可以写原因）。拒绝时Agent收到原因并调整做法。批准请求只能由发起该对话的人处理。

完全允许模式下直接发送内部消息时：收件人必须是已登记并绑定身份的公司同事（3.7）；发送前照常检查事项是否已取消、外发是否已暂停、附件的数据级别是否允许；同一事项对同一个人每个工作日最多催办一次；发出的消息在对话中显示，并进入日摘要。

分类与路径、对比器械、法规适用性、变更是否需申报、发补答复立场等判断，在过程中由Agent作出（请求批准模式下先提出建议、等人确认），写明理由、备选方案和依据，并在审核卡中逐条列出（2.2第2条、3.4）。人不同意时在对话中说明，Agent修改后重新提交。

仍由人决定的：风险接受；超出预算的费用；向监管机构或客户发出正式文件前的最终确认；需要管理层决定的路径、重大风险、大额费用和关键商业结论。

缺事实和证据冲突时仍要问人。资料中没有的信息（收件人、日期、编号等）不猜测（2.2第6条）；子Agent的证据冲突时停止写入并问人（6.2）。判断可以由Agent作出，事实不能编造。

「请求批准模式下关键判断先问」由系统提示词和技能规定。系统无法逐条识别哪一步是判断；兜底是最终审核卡逐条列出所有判断。

2.5 目标与运行

2.5.1 目标不等于一次运行

每项工作都以目标表达，例如「JoyBreath CPAP在2027-06-30前提交510(k)」「L08在美国持续合法可售」「本年度MDSAP监督审核无重大不符合项」。目标有负责人、截止日、验收条件和累计预算。

AI为推进目标会做多轮工作，下文称运行：可以是对话中的一轮，也可以是被事件唤醒的一轮，或者无人在线时在后台的一轮。一次运行是一段连续的执行，例如完成一次一致性检查、起草一份底稿。规则（调研3.1）：

  1. 运行结束不等于目标完成。 运行结束后，目标进入「待复核」；只有负责人确认验收条件已满足，目标才算完成。
  2. AI任务完成不等于业务完成。 例如「申报包装配完成」和「拿到许可」是两件事；业务结果（受理、批准、续期成功）必须有回执或官方记录作为证据，没有证据不显示为完成。
  3. 目标可以设置最多运行次数和累计预算，超出时暂停并交负责人决定。
  4. 负责人可以修改目标方向。 例如把「先做Pre-Sub」改为「直接准备申报」（更新）：
    • 修改后保存为新版本，之后的运行以新方向为准；
    • 旧方向不再进入AI的上下文，但保留在记录中；
    • 每次运行记录它所依据的方向版本。

2.5.3 唤醒

处于等待状态的目标由事件唤醒：资料到达、外部来函（发补信、受理通知、决定函、审核报告）、测试报告到达、到期日临近、人补充方向或作出决定、法规更新经确认影响本目标。规则（调研3.1、3.15）：

  1. 唤醒后新建一次运行，在该项目的工作区中从已知的状态继续，不重做已完成的部分。负责人不在线时在后台继续，结果交负责人审核。
  2. 同一事件只唤醒一次，不重复执行。
  3. 无法判断事件属于哪个目标时，交负责人确认，不猜测归属。

2.5.4 交还人工

负责人可以随时说「这件事我来处理」（调研3.6）：

  1. AI立即停止该事项的自动执行，不再以负责人的名义发请求、催办或写入；与该事项有关的提醒合并进摘要。
  2. 负责人处理完后说「交还给你」，AI读取人的处理结果（决定、补充资料、已完成的外部动作），从那里继续。
  3. 接管和交还都留存记录。

2.5.5 复盘与改进

  1. 复盘：每个注册项目结项、每次审核结束、每月维护周期结束时，AI生成复盘：目标完成情况、耗时、遗漏、返工、人工修改和退回的原因。
  2. 改进提案：AI根据复盘和人工反馈，提出对规则包、模板、检查项或工作方式的修改建议。人工修改和退回的原因按能力归类，是改进提案的主要来源（调研3.13）。
  3. 生效方式：提案经注册人员批准、评测集回归通过后才生效；生效时以追加新版本的方式进行，旧版本保留，可以回退；已生效的提案不能重复生效。
  4. 单次修改不自动变成全局规则。 人对某份草稿的修改只用于该项任务的后续草稿，除非经提案批准。
  5. 候选样例与评测集分开。 运行中发现的典型案例先作为候选样例，经注册人员确认后才加入正式评测集。
  6. 不降标准。 AI不得为了提高自评成绩而修改验收标准或评测答案。

2.6 项目工作区

每个注册项目和每个维护事项（例如「L08 FDA年度注册2027」）有一个项目工作区，相当于Claude Code工作的代码库：

  1. 内容：
    • 该项目的资料，引用资料库中的版本；
    • AI和人起草的文件、清单、计划、问题清单、决定记录；
    • 一份项目说明：产品、市场、路径、已作出的决定、注意事项。项目说明由AI随项目进展维护，每次工作开始时先读它。
  2. AI在工作区里工作：读资料、起草、修改、生成文件都在工作区中进行；每次保存形成新版本，记录是谁（哪个用户的哪次运行）改的、改了什么。
  3. 人看改动：交付时，审核卡显示本次相对上一个已审核版本的改动，可以逐个文件对比（3.4）。
  4. 定稿冻结：审核通过的版本可以定稿；申报包定稿后形成不可修改的快照，提交和发补答复都基于快照（R08、R10）。
  5. 不互相覆盖：两个人（各自的AI）同时处理同一个项目时，基于旧版本的保存不能直接覆盖，要先合并对方的改动。
  6. 可以恢复：任何已保存的版本都可以恢复，误改不会丢失已审核的内容。

  14. 界面风格：以对话为中心，简洁、安静。参考Codex、Claude Code、DSH的布局和交互方式，具体见《AI原生器械认证板块技术方案v0.4》第3章。

Agent运行环境的要求：

  1. 工具齐全，由本板块提供。 Agent像Claude Code一样有一套通用工具：读写和编辑工作区中的文件、在隔离的沙箱中运行代码（如表格统计、PDF拆分合并、Office文档的生成和转换）、检索和抓取网页（存档）、启动子Agent、维护计划与待办、加载技能、向人提问（6.3）。沙箱不能联网，没有凭据，只能读写交给它的文件。
  2. 业务后果只经本板块的业务工具。 写入业务记录、对外发送、保存工作区版本、定稿冻结，只能通过本板块的工具执行，按用户身份和动作级别授权（2.4）。
  3. 模型只经本板块的模型网关，由网关按数据级别路由（5.5）。
  4. 不默认外发。 界面和后台不包含任何遥测、使用统计或错误上报；引入第三方组件时逐项排查它默认会向外发送什么（5.5）。
  5. 每人隔离。 身份由公司登录统一认证；用户只能看到有权限的项目、对话和资料。首个可用版本先用由管理员建立的账号，之后接入公司统一登录（D21）。
  6. Agent的定义由本板块保存。 Agent的说明、技能和工具目录由本板块保存、审阅和发布；对话中、被唤醒时和评测时使用同一套定义。以后更换界面，Agent的行为不变。

以上各项作为常规验收的检查项（8.6）。

提醒通道的规则：

  1. 消息只放摘要和进入主入口的链接，不放资料原文。
  2. 即时通讯里的文字回复不构成审批（调研3.15）。人在企业微信里回复「同意」，AI提示在审核卡中操作；只有审核卡上的操作才是正式审批。

3.4 审核卡

AI交给人审核的每个结果都用同一种结构呈现：

  1. 结论：一两句话说明结果。
  2. 需要你做什么：通过、选择、补充或批准的具体事项。
  3. 过程中作出的判断：每条写明事项、Agent的选择、考虑过的备选、理由、依据（链接到原文）、风险高低。结构化结果中的对应字段为 decisions[]（6.4）。
  4. 改动：本次交付相对上一个已审核版本改了哪些文件、哪些内容，可以逐个文件对比（2.6）；有业务记录改动时列出改前和改后。Word、Excel、PDF可以直接预览版面并下载（3.6）。
  5. 关键依据：每条结论对应的原文摘录、文件名、版本和页码，点开可看原页。数值同时显示来源字段和单位（6.5 V7）。
  6. AI自检：执行了哪些检查、是否全部通过（见6.5）；以及评测结论（8.2）。
  7. 不确定事项：AI无法判断或依据不足的地方，明确列出。
  8. 操作：通过、修改后通过、退回并说明原因、追问、转交他人。

规则：

  1. 结论必须结构化提交。 审核卡的内容来自AI提交的结构化结果（6.4），写成普通文字的回答不算完成，也不生成审核卡（RV-01）。
  2. 审核后自动继续。 通过后，AI从中断处继续后续步骤，人不需要再发指令。退回时附原因，或者直接在对话中说哪里要改，AI在工作区中修改后重新提交；新的审核卡显示这次的改动（调研3.4）。
  3. 对话中的话不算批准。 人在对话中说「可以」「同意」「就这样」，不算批准请求的批准，也不算审核卡上的通过（IX-08、IX-14）。修改意见可以在对话中提出，Agent据此修改后重新提交（IX-11）。需要批准的事项仍要在界面上点击才生效（2.4）。

外发提案是一种审核卡，用于对外动作（2.4）：

  • 显示收件人、内容、附件，以及每个附件的数据级别；
  • 交给人之前，由程序校验关键字段：收件人必须来自登记的联系人或机构，附件不得包含禁止外发的资料；不通过的不生成提案（RV-02）；
  • 审核人可以修改后批准；批准后按2.4的发送规则执行。

3.5 过程可见性

  • Agent开始一项工作时列出步骤。每完成一步，在对话中用一句话说明做到了哪一步、下一步做什么。
  • 运行中，输入框上方显示当前状态：正在做什么、第几步共几步、已用时间，以及停止按钮；计划可以展开查看。后台运行时，进度同样写进对话。
  • Agent的工作过程（读了哪些资料、用了哪些工具、改了哪些文件）在对话中以可展开的形式显示，默认收起；人看的是结果、改动、依据和需要人做的事。
  • 人可以随时打断，纠正方向；AI停止当前步骤，按新方向继续，已完成的部分保留。
  • 需要时可以打开详情面板，查看本次运行的提案、目标状态、用量与费用、子Agent的结果、评测结果和完整事件（调研3.18）。详情面板默认收起。
  • 人可以随时问「你是怎么得出这个结论的」「你查了哪些资料」，AI按步骤说明。
  • 全部执行过程完整留存：读取了哪些资料和版本、调用了哪些工具、执行了哪些检查、用了哪个模型和规则包版本。这些记录供审计和复盘使用。

3.6 文件交付

Agent交给人的是审核卡，加上项目工作区中的文件改动，有时还有台账等业务记录的改动。报告只是交付物的一种。交付物分三类：

  1. 文件：可以直接使用的工作成果，包括按公司模板生成的Word、Excel、PDF，装配好的申报包，eSTAR填报单，预填表单，以及申报清单、检查报告、底稿、合规报告、迎审清单等。放在项目工作区中，带版本。
  2. 业务记录的改动：台账字段、提醒、项目等记录的变更，在审核卡中列出改前和改后。
  3. 回答与提醒：对提问的回答、到期提醒和进度说明，写在对话中；需要人处理的，仍以审核卡或批准请求提交。

审核卡和项目页的「文件」中，要能直接预览Word、Excel、PDF的版面，不只是文字对比，并可下载。对话中以交付卡片展示文件，可以逐个文件对比改动；审核通过的版本才能对外使用。人修改后的版本，无论是在工作区中直接修改，还是用WPS或Word改完再上传，都作为新版本保存，AI记录修改内容并用于改进。

3.7 与资料提供方协作

  • AI通过消息向研发、品质、采购、生产以及CRO、实验室、代理发出资料请求，写明要什么、为什么要、截止日期；到期未回复按规则催办，多次未回复升级给事项负责人。
  • 资料提供方回复文件或说明即可，不需要登录本板块的系统。
  • AI收到资料后检查是否满足要求，不满足时说明缺什么并再次请求。

通过即时通讯与内部同事协作的规则（调研3.15）：

  1. 身份要先绑定。 同事的即时通讯账号与公司账号通过一次性口令绑定，不能凭消息内容、群名或@自报身份。
  2. 提问和催办按权限模式执行。 请求批准模式下，向同事发消息先请人批准；完全允许模式下，可以直接发给已登记并绑定身份的公司内部同事（规则1），同一事项对同一人每个工作日最多催办一次。发往公司外部的消息每条都要人批准（2.4）。
  3. 回复绑定原请求。 同事的回复与原请求关联，唤醒对应的目标（2.5.3），同一回复只处理一次。
  4. 同事提供的信息先标为未核实。 同事的说明作为未经核实的资料使用，必须核对后才能写入事实；执行身份仍是事项负责人。

外部对象（CRO、实验室、代理）的渠道可能是邮件或对方的系统，待定（D03）。

3.8 少打扰

  • 不需要人动作的消息合并进日摘要。
  • 同一事项的多次提醒合并为一条，显示最新状态。
  • 紧急程度分三级：立即（法定时限、阻塞）、当日、摘要；只有立即级单独推送。

4.2 注册流程能力

R01 注册项目立项与倒排计划

  • 来源：P01、P02；URS-C-13；V0.4 FR25
  • 触发：注册人员在对话中设定目标（产品、型号、市场、路径或「待定」、目标日期）。
  • AI做什么：建立注册项目；从资料中补全产品信息；按市场规则包生成节点（测试、样品、合同、付款、报告草稿与终稿、提交、受理、发补、回复、批准、续费），从目标日期倒排计划日期，指定节点负责人；检查依赖和关键路径，发现目标日期不可行时说明原因和可选方案。
  • 交付：项目计划（节点、负责人、日期、关键路径、风险），以审核卡交负责人审核。
  • 人负责：目标日期由注册人员在设定目标时给出。节点负责人和是否调整计划，由Agent作出判断并写明理由（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。
  • 规则：每个节点必须有责任人和计划日期；改期保留原计划和原因；实际日期必须有证据，没有证据的节点不显示为完成。
  • 验收：用L08资料回填节点，资料中有的日期都带出处，资料中没有的节点（立项、送样、付款、草稿报告）标为缺少证据（V0.4 E23）。

R02 分类与申报路径研判

  • 来源：P04；URS-C-52；V0.4 FR13、FR14；组长插件②
  • 触发：R01建立项目，或注册人员提问。
  • AI做什么：
    • 美国：根据产品事实检索FDA产品分类数据库，给出产品代码、法规号、类别、是否豁免、路径（Traditional、Special、Abbreviated 510(k)、De Novo）候选；检索同产品代码已获准的510(k)，给出对比器械候选、理由和差异；读取同类产品510(k)摘要中的标准清单，作为证据规划的种子。
    • 加拿大：按分类规则给出器械类别候选和是否需要MDL；判断是否需要MDEL。
    • 其他市场：按市场规则包给出初判。
  • 交付：路径研判报告：每个候选附官方记录链接和匹配理由；信息不足时列出缺什么。
  • 人负责：分类、路径和对比器械由Agent选定，写明理由、备选和依据（请求批准模式下继续前先请人确认），注册人员在审核卡中审核；需要时转交同事复核。重大路径报管理层决定。
  • 规则：每个K号、产品代码都用官方数据回查，回查不到的候选丢弃；Agent给出选定的路径和理由，由人在最终审核中确认。
  • 验收：L08回放：产品代码LRK、21 CFR 872.5570、Class II、Traditional 510(k)、候选中包含SnoreRx K170825（V0.4 E01–E03）；组长评测集pd用例20例。

R03 Pre-Sub / Q-Sub 准备

  • 来源：P05
  • 触发：注册人员提出做Pre-Sub，或R02、R04发现关键不确定性。
  • AI做什么：汇总关键不确定性；检索历史反馈和同类产品公开信息；起草问题包骨架和材料目录；跟踪FDA反馈和会议纪要，把反馈转成计划和证据规划的调整。
  • 交付：问题包草稿、材料目录、反馈后的调整清单。
  • 人负责：是否做、问哪些问题，由Agent作出判断并写明理由（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。对外口径由注册人员确认；重大立场报管理层决定。
  • 验收：问题包覆盖注册人员确认的关键不确定性；每个问题有证据或缺口说明。

R04 适用法规标准与证据规划

  • 来源：P04、P06、P17；V0.4 FR15、FR11；组长方案第四节「合规矩阵」
  • 触发：R02路径确定后；产品设计、目标市场或法规更新时重新运行。
  • AI做什么：
    • 按产品特征和市场规则包列出适用的法规、指南、标准，每项带版次、FDA认可号（适用时）、过渡期和适用理由。
    • 推导证据需求：每类证据写明触发它的产品特征（如「接触口腔黏膜」触发生物相容性；「宣称储存期限」触发货架寿命；「含软件」触发软件文档；「带无线和联网」触发网络安全和无线共存）。
    • 每项证据记录覆盖范围（测试样品的型号、尺寸、配置）和代表性说明；没有说明时标「覆盖范围待确认」。
    • 对照已有资料，标出已有、缺失、过期（如标准版次已不被认可）。
  • 交付：证据规划清单（同时作为R06测试计划和R08申报清单的来源）。
  • 人负责：适用性和证据清单由Agent作出判断并写明依据，不适用的项写明理由（请求批准模式下继续前先请人确认），注册人员在审核卡中审核；需要时转交同事复核。
  • 规则：单一样品结果不得未经代表性说明推广到其他型号；有接受标准的才能判为满足。
  • 验收：L08回放：证据类别至少包括生物相容性（细胞毒性、致敏、皮内反应）、清洁验证、耐久性、货架寿命、材料特性、标签（V0.4 E04）；用CPAP示例验证有源器械章节（电气安全与EMC、80601-2-70、ISO 18562、软件、网络安全、人因、无线共存）全部被识别。

R05 研发资料法规审查

  • 来源：11-12业务访谈（注册人员的核心专业工作是审查风险分析是否到位、验证思路是否合理）；组长方案「法规三问」
  • 触发：研发等部门提交的风险分析、验证计划、测试方案、测试报告、标签说明书到达本板块。
  • AI做什么：按「风险是否受控、控制措施是否合理、验证与确认方案是否合理」三个问题预审，对照证据规划和适用标准找出缺口和疑点；核对报告与方案是否一致、报告引用的标准版次是否有效、样品是否覆盖申报型号。
  • 交付：审查意见：每条附原文位置、理由和依据，区分「可核对的缺项」和「需专业判断的疑点」。
  • 人负责：是否接受资料、退回研发补充的内容，由注册人员决定。风险是否可接受、验证是否充分仍只由人判断；Agent只列疑点，不写入测试结果或判定（见规则）。
  • 规则：AI不判断风险可接受、不判断验证充分，只列疑点；不写入测试结果或判定。
  • 验收：用注册人员退回修改过的真实方案做评测，统计检出、遗漏和误报（需样本，D09）。

R06 测试组织：机构比选、询价、送样与进度

  • 来源：P08、P09；URS-C-42、43；V0.4 FR30、FR31
  • 触发：R04列出需要外部测试的证据。
  • AI做什么：从机构库筛选有相应资质（如ISO 17025、ASCA）的机构；起草询价需求，经人批准外发对象后发出；汇总报价和周期生成比选表（原则上至少3家）；跟踪合同、付款、送样（样品型号和批次）、试验、草稿、审核意见、终稿各节点；审核草稿报告与方案、样品、标准是否一致；终稿进入证据库；项目结束时更新机构表现。
  • 交付：比选表、测试进度汇报、草稿报告审核意见。
  • 人负责：选定机构和对草稿报告的意见，由Agent作出判断并写明理由（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。超出预算的费用报管理层决定。询价发往公司外部，逐条批准（见规则）。
  • 规则：合同要写清交付物、周期、原始数据和修改责任（全景表角色分工）；各节点分别记录，不统称「测试完成」；询价属于发往公司外部的对外动作，逐次批准（2.4）。
  • 验收：L08各项测试的节点能回填并追到报告；超期节点全部提醒。

R07 资料收集与跨部门催办

  • 来源：P02
  • 触发：R04、R08产生资料需求。
  • AI做什么：向资料提供方发出请求（要什么、为什么、截止日）；按规则催办；收到后检查是否符合要求（格式、版本、签批、覆盖范围）；不符合时说明原因再次请求；多次未回复升级给事项负责人。
  • 交付：只在阻塞或升级时打扰人；资料状态进入周报。
  • 人负责：升级后的协调由事项负责人处理。催办按权限模式执行（3.7）。
  • 验收：每项资料请求有负责人和截止日；逾期当天提醒；升级记录完整。

R08 申报包规划与装配

  • 来源：P06；URS-C-30；V0.4 FR17；组长《申报清单模板》
  • 触发：注册人员要求，或R04完成后。
  • AI做什么：
    • 按路径生成申报清单：510(k)按eSTAR章节，加拿大MDL按申请内容要求，MDSAP迎审按审核清单；每项关联证据、负责人和截止日。
    • 把资料映射到申报章节，区分直接提交、需摘要或改写、仅内部参考三类；内部参考和禁止外发的资料不默认打包。
    • 装配申报包：附件命名、大小限制（eSTAR附件名不超过124个字符、单个附件1 GB、整份4 GB，待确认）、标准段落的版次和认可号、标签段落的说明书页码引用。
  • 交付：申报清单、缺件清单、装配好的申报包草稿和操作说明。
  • 人负责：清单是否完整由Agent作出判断并写明依据（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。是否进入提交由注册人员决定；向监管机构提交由人完成。
  • 验收：L08映射结果与实际eSTAR的23个附件对照，差异逐项列出；MSDS位置不明作为待确认项出现；清单要求而资料包中找不到的资料（如L08资料包中未见独立的风险管理资料）列为待确认缺件。这类缺件靠清单比对发现，一致性检查（R09）发现不了（RV-05）。

R09 申报一致性检查

  • 来源：P07；URS-C-31；V0.4 FR16；组长插件③；RV-05
  • 触发：注册人员要求，或装配完成、资料更新时自动运行。
  • AI做什么：按一致性检查的三层执行（6.6）：
    1. 程序规则先跑标准检查项：同名文件不同版本、编号的近似变体、申请人与联系人、关键参数跨文件一致、型号配置（材料、颜色）一致、引用文件与附件清单、实验室报告结论栏、接触时长与使用期限。
    2. AI按检查项从文件中抽取字段：型号与配置、预期用途与人群、材料与色母、关键参数、使用期限与储存期限、清洁步骤与参数、对比器械编号、申请人与联系人、报告编号与日期、标准版次。抽取结果以结构化陈述提交（6.4），由程序比对。资料多时，按资料类别启动子Agent并行抽取（6.2）。
    3. AI对候选差异复判：区分真实不一致、不同试验条件或用途（例如塑形后冷却与清洗冲洗的水温不同）、术语差异，并说明理由。
  • 交付：缺件和不一致清单，每条附至少两处原文位置，注明由哪一层发现、AI复判的意见；需要人解释的事项（如接触时长与使用期限的关系）单独列出，不判断对错。
  • 人负责：差异的真伪和处理方式由Agent给出判断和理由（请求批准模式下继续前先请人确认），注册人员在审核卡中逐条审核。需要人解释的事项仍由人判断对错（见交付）。
  • 规则：抽取值必须逐字出现在原文；比对由程序完成，不由AI判断；数值带单位比对（6.5 V7）；已提交文件不修改；只有数值没有接受标准的标为待评价；误报登记并用于改进规则（6.6）。
  • 验收：
    • L08已知差异全部检出：K170825与K170285；L08-TB色母蓝色与紫色；冲洗温度20–25°C与25~30°C；Cover letter联系人不同；MSDS未列入eSTAR附件（V0.4 E05）；SGS材料报告结论栏为「/」作为提示项；接触时长与使用期限作为交人解释项。
    • 注入缺陷全部检出（E07）；组长评测集cx用例20例。
    • 同时统计误报率（8.3）。
    • 规则须在第二个产品（如CPAP）的资料上验证，不能只用L08校准。
    • 参考：RV-05中，程序规则在0.1秒内发现了上述已知差异中的全部可比对项，另发现2处外层与内嵌版本差异（Device Picture小标题、货架寿命报告表格编号），待注册人员确认后加入评测集。

R10 提交准备、提交记录与审评跟踪

  • 来源：P10；URS-C-32、33；V0.4 FR18、FR19
  • 触发：注册人员确认可以提交。
  • AI做什么：生成提交操作说明；人提交前冻结申报快照（文件版本与sha256清单，清单再算哈希，不可修改）；人提交后核对实际提交文件与快照是否一致；记录回执、受理号；跟踪审评阶段（技术筛查、实质审评、补充信息请求、交互式审评、决定）和期限（如补充信息请求的答复期限，待确认）。
  • 交付：提交快照、提交记录、审评状态汇报和下一步。
  • 人负责：向监管机构提交、与审评员沟通由人完成。提交准备的结果由注册人员在审核卡中审核。
  • 规则：没有回执或确认记录时，不显示为已受理；保存时间、文件日期不等于提交日期。
  • 验收：L08：识别eSTAR附件与外层文件的4处版本差异；没有的回执标为缺少证据（V0.4 E09）。

R11 发补与审评问题应答

  • 来源：P11；URS-C-60、61；V0.4 FR19；组长插件④
  • 触发：收到FDA、加拿大卫生部或审核机构的问题函。
  • AI做什么：登记来函和截止日，建立倒计时；把问题拆为逐项，每项引用原文；为每项检索历史应答、证据和申报快照；判断每项属于「已有证据可答」「需研发补充资料或测试」「需确认答复立场」；答复立场由Agent给出并列入审核卡；向资料提供方发请求；起草答复底稿，引用回到原文；多轮答复分别留存。
  • 交付：问题清单（逐项负责人和截止日）、答复底稿、需要补充的事项。
  • 人负责：答复立场由Agent作出，写明理由、备选和依据（请求批准模式下继续前先请人确认），注册人员在审核卡中审核；需要时转交同事复核。重大风险报管理层决定。向监管机构递交由人完成。
  • 规则：拆项不得遗漏；引用不回到原文的段落丢弃；重新拆项不得静默替换已确认的问题项。
  • 验收：组长评测集dx、dr用例各20例；有真实发补记录时用真实记录验收（D09）。

R12 获证归档、维护移交与项目复盘

  • 来源：P12；V0.4 FR20
  • 触发：收到许可决定。
  • AI做什么：记录决定（类型、日期、许可编号、决定函），与官方公开记录核对；更新产品合规主数据（型号×市场授权状态）；生成该产品在该市场的维护义务（注册、列名、年费、代理人、UDI、标签控制、变更评估、警戒），建立对应的维护事项并附移交清单，按当前对话的权限模式执行（2.1），之后由维护Agent负责；生成项目复盘（路径、周期、费用、发补问题与答复、经验和可复用范围），进入案例库。
  • 交付：维护义务清单、项目复盘。
  • 人负责：维护义务由Agent列出，注册人员在审核卡中审核；需要时转交同事复核。复盘经注册人员确认后入库。
  • 验收：由K253845生成的维护义务覆盖企业注册与列名、年度注册与年费、美国代理人、UDI与GUDID、标签控制、变更评估、警戒（V0.4 E11）。

4.3 体系维护能力

M01 产品合规主数据与证照台账

  • 来源：P19、P20；URS-C-10、12、14；V0.4 FR21；组长《主表与数据字段》《现有台账与清洗规则》
  • 触发：持续；资料、请求、决定、变更到达时更新。
  • AI做什么：维护产品—型号—市场—证照的对应关系（含品牌、UDI-DI、UPC、包装层级）、证照台账（类型、编号、持证主体、范围、生效与到期日、费用、负责人、来源）和维护义务；从现有Excel台账首次导入（按组长清洗规则：去重、冲突报告、先预览后导入）；与官方公开数据定期比对；按规则安排到期提醒。
  • 交付：人通过对话查询（如「哪些证照90天内到期」「JB-C1在哪些市场可售」）；关键事实变化以审核卡交注册人员审核。
  • 规则：同一型号同一市场只有一条授权记录；「可售」「已列名」必须关联证照；内部与公开数据不一致时先标待核实，不直接表述为违规；导入后原Excel台账只读归档（全景表「唯一入口」）。
  • 验收：公司现有全部证照录入后试点期间逾期为0；L08主数据能回答「哪些型号、以哪些品牌、由哪个企业以哪个K号列名、美国代理人是谁、UDI状态如何」（V0.4 E12）。

M02 美国企业注册、列名、年费、美国代理人、UDI

  • 来源：P13；URS-C-41；V0.4 FR22、FR23
  • 触发：每年10月1日至12月31日企业年度注册窗口（待确认）；列名信息变化；新型号或新品牌上市；美国代理人合同到期。
  • AI做什么：查询FDA企业注册与列名、GUDID公开数据，与台账比对；生成年度注册和年费待办；按主表预填企业注册、列名、GUDID表单，并列出与台账和证照不一致的项；核对标签、外包装、列名专有名称、GUDID与获准范围是否一致；人完成后核对凭证。
  • 交付：核查报告、表单预填稿、待办。
  • 人负责：在官方系统提交并上传凭证由人完成。核查结果和表单预填稿由注册人员在审核卡中审核。
  • 验收：L08公开数据核查结果（列名企业、注册号、到期年份、美国代理人、4个专有名称、GUDID未查到记录、申请人未查到注册）全部列出且标为待核实（V0.4 E12、E13）。

M03 加拿大MDL、MDEL、年度续期与变更

  • 来源：P14；URS-C-41；V0.4 FR27
  • 触发：MDL年度续期（待确认时间）；MDSAP证书状态变化；名称、型号变更；进口商和分销安排变化。
  • AI做什么：维护MDL、MDEL、MDSAP证书的状态和到期；判断MDEL是否需要（持有MDL并通过持MDEL进口商销售的Class II制造商可免，待确认）；按主表预填MDL申请与变更表单；关注法规变化（如2026-12-14生效的SOR/2026-110要求MDEL申请附供应商清单，待确认）；双语标签核对。
  • 交付：续期和变更待办、表单预填稿。
  • 人负责：提交由人完成；高管声明由授权人签署。续期、变更和许可结构的判断由Agent作出并写明依据（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。
  • 验收：用真实或已完成的加拿大项目回放（D05）；续期提醒逾期为0。评测包括许可结构、许可修改和年度许可审查（《AI原生器械认证板块数据与评测方案v0.1》第6.2节）。

M04 其他市场注册与代理维护

  • 人负责：是否进入、投入由人决定，需要时报管理层。选择代理由Agent给出候选和理由（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。
  • 验收：每启用一个市场，有一个项目的资料清单经注册人员确认。

M05 质量体系审核准备与整改跟踪

  • 来源：P16；URS-C-63；V0.4 FR24

  • 交付：迎审清单与缺口表、整改跟踪汇报。
  • 人负责：证据是否充分、现场应对由人决定。整改方案由Agent起草并给出判断（请求批准模式下继续前先请人确认），注册人员在审核卡中审核。重大不符合报管理层。

M07 变更影响评估

  • 来源：P18；URS-C-62；V0.4 FR05；组长插件⑤；调研3.7
  • 触发：产品设计、材料或色母、供应商、生产场地、工艺、标签和说明书、品牌、型号、软件和固件、预期用途宣称发生变化（由资料提供方通知或AI在资料中发现）。
  • AI做什么：识别变更类型；通过台账和证据关联找出受影响的型号、市场、证照、列名、证据；按每个市场的规则包逐步判断（美国按FDA变更指南的判断流程，加拿大按重大变更规则，UDI是否需新器械标识）；涉及多个市场时，由子Agent按市场并行判断，主Agent汇总并写入（6.2）；汇总自上次获准以来的累积变更；生成同步待办（列名、MDL、GUDID、510(k)）。
  • 交付：变更影响评估，每个市场一份初判（可能需申报、内部记录即可、无法判断则交人审核），附每一步的依据。
  • 人负责：各市场是否需要申报由Agent作出判断并写明依据（请求批准模式下继续前先请人确认），注册人员在审核卡中审核；需要时转交同事复核。重大变更报管理层决定。
  • 规则：Agent给出每个市场的判断和依据，由人在最终审核中确认；已获准资料和历史评估不覆盖。
  • 验收：V0.4 E14的6个情景（新增贴牌品牌、更换色母、修改清洁温度、宣称治疗OSA、新增尺寸、合同制造商变更场地）的初判与注册人员标注一致。

M09 法规、指南、标准更新监测

  • 来源：P03；URS-C-50、51；V0.4 FR28；组长插件①

事实的有效期与修订（更新）：

  1. 人确认的事实可以带有效期、锁定标记和修订记录。例如一项授权在某日之前有效，一项临时约定到期后失效。
  2. 过期的事实不再作为事实使用，但保留在记录中。
  3. 锁定的事实只能由负责人修改；修改时保留与旧版本的关联，不覆盖历史。
  4. AI可以从资料、已完成的事项和沟通记录中提出事实候选，附证据片段，标为待核实，不能自动确认。
  5. 人对候选可以确认、改写或拒绝，并可设定处理期限。
  6. 两条事实互相冲突时，交负责人裁决；重大冲突报管理层。

5.3 每项能力的知识策略

每项能力配一份知识策略，写在该能力的技能中；其中能由程序判断的部分（引用数量、引用格式、是否检索过），在提交审核时由系统检查，而不是只写在给AI的提示里（调研3.9）。策略规定：

  1. 可以检索哪些资料（资料库、产品、项目范围）；
  2. 是否必须先检索再回答；
  3. 引用规则：每条结论至少引用几处原文，引用必须带文件、版本和页码；
  4. 缺少资料时怎么办：交部分结果并列出缺失，或者停止并报告。

资料库为空或检索不到时，结果中明确写「没有找到」，不编造证据。

5.5 数据边界

  1. 按数据级别路由。 系统按资料的数据级别，把模型请求路由到允许的模型；指向未批准端点的请求直接拒绝（RV-05）。
  2. 资料分级。 资料分为公开、内部、保密三级，入库时标注，默认按内部处理：
    • 公开和内部资料可以发往已批准的外部模型；
    • 保密资料只发往本机或内网模型。

2026-11-17项目负责人确认：当前的器械认证材料（含L08申报资料）不涉及需要保密的内容，定为内部级别，可以用于开发、测试和已批准的闭源模型。将来出现需要保密的资料（例如研发设计资料），定为保密级别。

  1. 不默认外发任何数据。 遥测、错误报告、更新检查、使用统计默认关闭，启用须技术负责人批准并登记。引入外部代码或组件时，逐项排查它默认会向外发送什么。已知的例子：
    • 参考项目默认把错误报告发往作者社区的服务，需要手动关闭（RV-01）；
    • 第三方组件和前端依赖库可能自带使用统计或错误上报，引入时检查并关闭（3.1）。
  2. 执行记录不含正文。 执行事件只保存对象编号、状态和摘要，不保存资料正文、原始工具参数和凭据；AI的对话状态只在服务端保存（调研3.17）。
  3. 密钥不外露。 模型和接口的密钥不进日志、结果文件和对话。
  4. 按人可见。 登录用户都是注册部门的成员，按项目和资料权限查看。销售人员和管理层不登录。资料提供方不登录。

5.6 业务语义层

AI查询业务记录（如「哪些证照90天内到期」「JB-C1在哪些市场可售」「本月逾期节点有几个」）时，不自己拼写查询，而是通过业务语义层完成（更新）：

  1. 概念目录。 维护一份带版本的概念目录，写明每个业务概念的定义、对应的字段、单位和来源。例如：
    • 「到期」按哪个日期字段计算；
    • 「可售」需要满足哪些条件；
    • 金额和期限的单位是什么。
  2. 先判断能不能回答。 AI先检查问题能否用已审阅的查询回答；不能回答时列出缺失的定义，请人澄清，不猜测口径。
  3. 只执行审阅过的查询。 查询模板经注册人员确认后才能使用；查询只读，有返回行数和时间限制。
  4. 结果分三种。 每次查询的结果标为完整、部分或无法回答，并附回执：使用的口径、范围、概念目录版本、数据缺口和截断情况。回执进入执行记录。
  5. 单位由目录给出。 结论中的数值按概念目录中的单位换算和显示，与6.5的V7检查配合。验证中出现的「分」当「元」错误（RV-01），属于这一层要防止的问题。

适用于M01、M02、M03、S01、S04等以查询台账为主的能力；首版的概念范围和查询模板在《AI原生器械认证板块技术方案v0.4》中列出，经注册人员确认。

5.7 资料进出与交付物

AI要完成工作，资料要进得来，交付物要做得出来，并能送到需要的地方：

  1. 批量导入：可以一次导入整个申报包（压缩包或文件夹，含嵌套的压缩包和eSTAR内嵌附件）。系统自动去重、识别资料类别、解析并标注数据级别，以清单形式汇报导入结果，无法识别的文件单列。
  2. 对话中的附件：用户在对话中上传的文件进入本板块的资料库，处理方式与批量导入相同。
  3. 邮件转入：监管机构来函、受理与审评通知、实验室报告、报价等，通过专用邮箱转入，自动入库，并作为唤醒事件（2.5.3）。接入条件待定（D03）；接入前由人转发或上传。
  4. 付费标准：ISO、IEC等标准全文不能从公开网页取得，由公司提供已购标准的副本入库，在公司的授权范围内使用（D17）。
  5. 文档生成：
    • 按公司模板生成Word、Excel、PDF交付物，如Cover letter、510(k)摘要、清单、合规报告、发补答复底稿；
    • 装配申报包，处理命名、合并、书签和大小限制；
    • eSTAR是加密表单，不由程序直接填写：AI准备按章节组织的填报内容和附件清单，由人在eSTAR中填写。
    • 生成的Word、Excel、PDF在审核卡和项目页中直接预览版面并可下载（3.6）。
  6. 改稿回收：人修改后的版本上传或同步回资料库，系统比对与AI草稿的差异，按能力归类，作为改进的输入（2.5.5）。

6 AI执行与质量控制

6.1 执行方式

  • AI以多步执行的方式完成任务：理解目标 → 规划步骤 → 调用工具取资料和数据 → 处理 → 执行确定性检查 → 自查 → 提交结构化结果。按权限模式，在需要批准时暂停，等人处理后再继续；最终结果以审核卡提交。
  • 按技能工作。 每项能力对应一份技能（5.2）。Agent根据任务加载相关技能，按其中的步骤、证据要求和检查执行；步骤由Agent自己规划，技能给出方法和必须满足的要求，不规定死板的流程。
  • 能用确定性规则完成的步骤（期限计算、编号回查、字段比对、清单对照、单位换算）由程序完成，模型只做需要理解文字的部分。
  • 在对话中做，等待时在后台继续。 人在线时，Agent在对话中直接完成工作。需要等待外部时，Agent登记在等什么并结束本轮；事件到达后，在同一个项目中继续（2.5.3）。
  • 中断后能从已完成的步骤继续；同一请求不重复建单或重复执行；结果不确定时先核对，不盲目重放（组长Harness需求HN-10、HN-11）。
  • 后台运行有执行权期限：失去执行权的进程不能再写入；取消能传到正在进行的模型调用和工具调用；执行事件按顺序先保存，刷新或重连后可以从断点继续查看（调研3.8）。
  • 组长曾暂定「阶段1不引入Agent循环」。本文的形态要求AI自主完成多步工作，因此默认使用多步执行，但每一步都受第2章动作级别和本章检查的约束。
  • 看图核对：标签、包装、器械图片、说明书插图中的符号、文字和颜色需要看图核对，不能只靠文字识别。模型网关支持图像输入；看图核对使用通过模型验收的多模态模型。

6.2 主Agent与子Agent

需要分头调查的任务，由主Agent并行启动多个子Agent（即此前所称的专职AI），每个子Agent负责一个方面，例如一致性检查按资料类别分工、变更评估按市场分工（调研3.7）。技能中写明建议的分工。规则：

  1. 子Agent只能读取资料和在工作区中起草；业务记录的写入和对外动作只由主Agent通过本板块的工具执行，受审批规则约束。
  2. 子Agent共享主Agent本次运行的预算。
  3. 某个子Agent失败时，主Agent在汇报中说明哪部分未完成，不能把部分结果当作完整结果。
  4. 子Agent意见冲突时停止写入（更新）。 有两种情况：
    • 两个子Agent对同一字段的证据不一致：主Agent停止写入，把冲突标为未解决，并向人说明是哪些字段有冲突、各自的依据，请人确认；
    • 子Agent读取的资料版本不同：主Agent停止写入，重新读取最新版本后再判断。

冲突未解决前，结果不能交付为完成。

6.6 一致性检查的三层

一致性检查（R09，以及M06、M08中的版本核对）分三层完成（RV-05）：

层做什么说明
程序规则按标准检查项做确定性比对快，结果可复现。验证中，程序规则在L08资料上发现了8条人工核实差异中的7条，用时0.1秒；漏掉的一条需要清单比对

  1. 标准检查项以规则库管理，带版本；新增或修改规则须用评测集回归。

  4. 首版标准检查项：

    • 编号的近似变体；
    • 申请人与联系人；
    • 关键参数（温度、时间、尺寸、期限）跨文件一致；
    • 型号配置（材料、颜色）一致；
    • 引用文件与附件清单；
    • 实验室报告结论栏；
    • 接触时长与使用期限（交人判断）。

6.7 预算与停止

  1. 每次运行设步数、token和费用上限；每个目标设累计上限；每月设总费用上限和告警阈值，额度由管理层确定（D13）。
  2. 预算按能力分别设定。估算时要考虑每一轮都会重发完整上下文，多步查证的任务用量随轮数快速累积。验证中一次7步的只读查询累计约3.3万token，超过了3.2万的单次预算（RV-01）。
  3. 达到单次上限时停止，由系统生成中途停止汇报（3.3）。
  4. 费用无法计算时，不自动追加调用，并标为「计量不完整」（RV-01）。
  5. 达到月度上限后，新的请求在发出前被拒绝，进行中的事项交回负责人；调高上限不会自动恢复已暂停的事项（调研3.14）。

6.8 防过度依赖

  • 每季度在AI交付中植入已知缺陷，统计审核人的检出率。
  • 审核卡单设「未核实事项」区。

8.2 评测维度与合成规则

每次运行按七个维度评测：任务完成、答案质量、依据充分、工具可靠、策略遵守、效率、协作质量（调研3.12）。规则：

  1. 先做确定性评测：工具调用是否成对完成；只读模式下是否有写入；对外动作是否在人批准之后；结论引用的证据是否出现在成功的工具结果中；结构化陈述与原始记录是否一致。
  2. 语义复核只能降分。 语义复核由另一个家族的模型完成，只能降分、不能升分；复核失败时，「通过」降为「需复核」。
  3. 未核实的陈述不能评为通过。 没有被独立核实的自然语言陈述，答案质量最高为「需复核」。
  4. 评测可复现。 评测报告按运行、评测方案版本和输入指纹存档；同一输入重放得到同一结果。
  5. 评测结果有用途。 评测结论显示在审核卡上（3.4），并作为等级晋降的依据（2.3）。参考项目的评测不影响自主程度，这一点是本文加强的。
  6. 没检查不等于没问题（更新）。 没有读取的资料不能报告为「不存在」，没有检查的文件不能报告为「没有问题」，没有测量的维度不能当作得分低；这些情况都标为「未检查」或「未评测」。
  7. 评测失败不影响运行结果（更新）。 读取或生成评测失败时，保留运行结果，说明失败原因，只重试评测，不重新执行任务。
