# PR-34 M02 美国公开资料核查与定时唤醒

美国维护目标负责人在项目首页的「工作目标」启用或停用定时核查。后台按项目法域计算月份及年度注册窗口。负责人离线时在新维护对话使用固定版规则包核对公开回执、确认事实及内部归档，按照现有权限设置年度站内提醒并提交审核。停用停止后续扫描，已产生的对话保留。规则包和技能均为开发草稿，待注册人员确认。[决定 D-066](../决定记录.md#d-066-m02-定时核查与公开回执)

`official_lookup` 补充企业注册及列名按 K 号和产品限定、完整法定名称登记查询、以及产品代码结合 K 号或商品名的 openFDA UDI 查询。只在已授权的 FDA 托管地址查询。核查将官方数据、公司归档和历史观察分开，保留来源、查询时间与失败原因。开发验收使用公开 L08 线索和独立合成档案，禁止真实发信。[FDA 企业注册与列名字段](https://open.fda.gov/apis/device/registrationlisting/understanding-the-api-results/) · [FDA UDI 字段](https://open.fda.gov/fields/deviceudi_reference.pdf) · [E12、E13 用例](../../evals/m02/README.md)

## 验收

- `pnpm test:int apps/backend/src/goals/m02-schedule.int.test.ts` 检查浏览器 Cookie、CSRF、负责人、版本重复、法域日界线、窗口前唤醒、规则包固定，以及项目关闭或工作区升密与扫描并发的结果。覆盖重新启用时补做未取得运行权的周期，和实际执行后仍去重。模型网关既有回归在发送前重新核对当前资料级别。
- 技能定义单测随已批准的实时查询范围更新。它检查 `official_lookup`、公开查询条件、成功零条的限定表述和开发草稿状态。正式环境禁止开发草稿的测试继续执行。
- `pnpm test:m02` 先回查官方公开 UDI 非空样本，验证公开记录键与主 DI。有浏览器的 M02 走查在负责人启用定时核查并退出后运行。由后台生成新对话，核对 FDA 的三个查询和档案，验证覆盖年度注册和年费的一项合并站内提醒及待审核卡，并检查未调用消息或外发提案工具。1440×900 截图与原始回执留在隔离验收环境。
- 设计稿 03 的项目首页沿用现有卡片和文字按钮。「工作目标」增加负责人启停入口。附独立走查的合成工作台截图，不含资料内容。[1440×900 启停截图](../evidence/pr-34-m02-schedule-1440x900.png)
- `pnpm docs:html` 更新离线文档。仍运行原有通用检查、M02 专项和标准 R09、M02、双模型核实及浏览器错误编号走查。
- Lan 授权 PR-34 和 PR-35 在独立验收机用已有 Cursor 团队账号验收。由正式验收入口传入 `CERT_CURSOR_ACCEPTANCE=PR-34` 或 `PR-35`，以及 `CERT_CURSOR_ACCEPTANCE_HEAD` 的完整候选提交编号。预览和后台核对当前虚拟机报告、候选提交的 PR 编号、验收提交、双亲、合并树及干净工作树后才启用。PR-34 专项先运行 `pnpm walkthrough:real --cursor-probe` 验证合成项目。回执记录实际主模型、网关通道、提交、基线和合并树。主 Agent 使用 GPT-5.6 Sol，核实直接通道使用 Grok 4.7，网关核实使用 Claude Opus 5.5。三者均由 Cursor CLI ACP 调用。
- 只在开发模式及根目录带专用标识的独立 Linux 客体启用。使用经确认的团队隐私配置及 Cursor 内置模型，外发只含公开或内部级资料。所有业务工具仍由 cert-board 执行。Cursor 自身关闭文件、Shell、网页和 MCP 能力。回执分别给出已确认的未发送笔数及待核账笔数，两者合计等于 Cursor 网关记录的请求总数。[Cursor 隐私与零数据保留说明](https://cursor.com/docs/enterprise/privacy-and-data-governance)
- ACP 启动握手在进入派发复核前失败时，可以新建一次连接。每次真正发送前仍执行相同的权限、执行权和资料级别检查。合成预检若因文字回合结束而未送审，Chromium 会补发一次继续操作的消息，再核对两页原文、保存、自查、审核卡和实际批准。
- Cursor 主 Agent 的回执格式错误和原生工具阻断分别记录。只有确认收到的回合格式错误才允许在同一运行中复试一次，复试重新通过派发校验并使用独立请求编号。已派发的请求逐笔留在待核账簿，原生工具阻断或其他派发后失败直接结束本轮。诊断改动尚未确认能解决上次 M02 真实走查的失败。
- 网关将回执拒绝细分为空回复、JSON 语法错误、回合结构错误和调用了本轮未提供的工具。类别与对应计量记录在同一事务保存，便于区分首次和复试请求。按失败运行的 `usage_ledger.run_id` 查询，再用账目编号关联 `audit_log.target_id` 下的 `model.cursor_reply.*` 动作。回复正文、工具参数和解析异常原文不入审计；费用仍列待核账。
- 新快照的首次合成请求和复试均记录 `invalid_json`。主 Agent 的 JSON 回复要求移至 ACP 文本开头，原请求以带角色的 JSON 附在后面。全回合校验和工具许可照常执行，核实仍使用其既有回执模式。离线协议测试直接核对发给合成 ACP 进程的文本。
- 当前验收机用无推理握手实测，ACP 协商为 v1，未声明系统提示附加能力。主 Agent 为每次派发生成独立编号，接受同编号的唯一末尾回复帧，并对帧内的完整 JSON 和工具目录照原样校验。帧前普通进度文字留在传输层；帧不完整、重复、带另一份结构化内容或带上轮编号均拒绝。兼容原完整 JSON 回执。格式失败的日志可区分无帧文字与错误帧，核实回执和原生工具拦截沿用原门禁。[ACP 协议能力](https://agentclientprotocol.com/protocol/v2/initialization)
- 独立复审后，在最后一次验收范围检查之后复核资料级别、运行身份与租约。同步核对计量拦截和取消状态后写出 ACP 请求。完整帧超出输出预算时可用原完整 JSON，字节限制相同。帧边界在旧 Markdown 围栏处理之前核对。M02 用例从本次官方回执取准确拼写，按原值、版本、页码和对应 JSON 字段的逐字引文检查审核卡。商品名引文核对同一列名记录的专有名称数组。
- 一轮复验中，M02 专项和标准 R09 已通过，标准 M02 因预览接口在数据库连接断开后退出而中断。接口现在处理已租出连接的错误事件，原查询依旧返回失败。集成测试验证测试连接断开后服务继续借用新连接。
- 随后的复验通过通用检查和 Cursor 合成浏览器预检。M02 专项登录时 PostgreSQL 恢复约 14 秒，登录返回 `57P03`。更早的集成测试也记录过同样的 PostgreSQL 恢复信号。故障时的探针进程身份未留存。开发和预览数据库由容器 init 回收孤儿进程，直接运行 `pg_isready` 检查 PostgreSQL 的本地 TCP 监听。间隔、超时、重试次数和服务就绪条件沿用原值。[相同容器故障机制记录](https://github.com/super-productivity/super-productivity/issues/9695)
- 修复容器探针后的独立复验通过通用检查、Cursor 合成预检和正式 M02 专项。标准 R09 读取原文后以文字结束，计划仍有待办，未形成待审核卡。Cursor 主 Agent 只有在原运行的计划未完成且送审工具仍可用时，才用既有回执和当前工具目录续做一次。这与结构错误恢复共用同一次复试额度，仍逐笔计量和校验派发。经浏览器批准或外部核实结论恢复原运行时，继续沿用最新计划和已用的复试额度。后续送审与浏览器批准需由正式走查实际验证。
- Cursor 验收账号只在指定走查网页与库的回环连接启用。最后一次路由查询同时检查资料级别与 Agent 执行租约。单个 M02 目标锁超时后，仍继续检查其他目标，扫描结束后报告未完成项供下次重试。
- 两轮标准 R09 和 M02 已完成浏览器审核，核实直连 Grok 有回复。网关侧 Claude 派发后记录 `MODEL_CURSOR_REPLY_INVALID`。无工具的核实通道按业务要求校验 `{text, claims}`，纯文字或残缺 JSON 无法验证判断字段，仍返回格式错误。主 Agent 的工具回合使用原动作模式。出网检查、计量和回执出处核查照常执行，失败只存登记的错误类别。
- M02 的待核实要求验收结构化状态和实际可见内容。申请人及 UDI 两个结论仍须为 `unverified` 并引用各自官方档案，不确定事项须逐条显示在审核卡的对应区块。上一轮待审卡有三条明确的不确定事项，用了不同措辞，旧正文短语检查因此失败。报告保留该轮结果。
- 列名登记号是企业列名查询的必要参数。验收逐项校验列名机构、登记号、年份、美国代理人和商品名称的 `unverified` 状态及本次列名档案引用，并按运行固定的规则包与项目法域校验提醒的完整日期。
- 列名到期年份在审核卡以文本保存并使用空单位，引用仍保留 FDA 档案中的数字原文。M02 专项逐条核验列名字段的所有主张，拒绝错误类型、非空单位、错误引语和夹带的错误主张。查询失败、缺字段或没有可引证档案时，走查提示要求登记在不确定或缺失事项中。证据不足时保留已有证据并说明待补项。正式专项仍要求三份成功的本次官方档案。
- 团队账号在每次实际派发前复核验收报告和工作树。网关确认请求未发出时，核实记录和界面同样标为未发送，使用量统计和当日外发档案排除该笔。预派发检查时间保留在只追加的审计记录中。已派发但回执不完整的请求保留待核账。

## 没做什么

- 当前定时运行使用开发版 Agent 定义。正式环境还需发布 Agent 定义、M02 技能与规则包。数据源无结果时由人工复核适用性。付款、签名、监管门户操作和对外联系由人处理。
- 当前确认规则为 V1 与 V3，V2 可用独立编号核验工具，V6 取具有计算回执的结构化期限。V4 全面的资料语义对照未实现。单个目标沿用一项站内提醒。
