# 本地 Linux 虚拟机验收

## 环境

验收机以 Ubuntu 24.04 的独立 Linux 内核启动，使用 QEMU/KVM。Windows 上已有的 WSL 只承载虚拟化进程。应用、Docker、浏览器、测试数据库和工作树都在客体里。Windows 的日常工作台与 Lan 稳定预览各自运行。

镜像使用 Ubuntu Cloud Images 的 amd64 发布版，先用 Ubuntu 云镜像密钥环核验 `SHA256SUMS.gpg`，再核对镜像摘要。使用 QEMU 的 NoCloud 光盘设置独立账号和 SSH 公钥。宿主通过 WSL 中的 SSH 客户端连接 QEMU 控制容器的回环入口，主机公钥从客体启动控制台取得并固定。客体没有 Windows 工作目录共享挂载。宿主用于启动客体的文件位于仓库 `.local/test-vm/`，客体磁盘在 `cert-board-acceptance-vm` 本地 Docker 卷。

虚拟机准备 Ubuntu 自带的 Docker、Compose、Git、Node 24.22.2、pnpm 9.15.9 和 Playwright 的 Chromium。虚拟机根目录标记为 `/etc/cert-board-acceptance-vm`。准备完成后关机保留基础磁盘。每次验收在前一个客体已关机时，从宿主执行 `node .local/test-vm/start-fresh.mjs <本次实例名>`，从基础磁盘建立新的 QCOW2 差异盘后启动。基础磁盘保留运行时和浏览器，可复用的软件包属于缓存。项目工作树、数据库卷和验收日志随验收实例独立生成。

客体使用 Ubuntu 24.04 的 HWE 内核。沙箱需要 Landlock ABI 6 或更高，启动验收前直接检查客体 ABI。运行报告记录内核与 ABI。Docker 容器和现有沙箱安全配置沿用原方案。[Ubuntu HWE 内核](https://ubuntu.com/kernel/docs/reference/hwe-kernels/) · [Landlock ABI](https://docs.kernel.org/userspace-api/landlock.html)

## 每个 PR 的操作

1. 在宿主从 GitHub 获取最新 `main`。记录 `main` 和最终 PR 提交的完整编号。生成包含两条分支的 Git bundle，通过回环 SSH 发给干净的验收虚拟机。GitHub 凭据、日常 `.env.local` 以及原始 L08 文件留在宿主的授权位置。
2. 在客体运行 `scripts/acceptance-vm.mjs`，同时交付同目录的 `acceptance-vm-policy.mjs`。两文件来自当前可信 `main`。首次启用时使用配置 PR 的脚本。从 bundle 校验两个提交，算出无冲突的合并代码树，再建立干净的验收提交和工作树。报告同时记录两个真实提交、合并代码树和本机验收提交。
3. 运行锁定依赖安装、lint、类型检查、单元测试、构建、Python、Agent 评测、本地依赖启停、集成、浏览器、密钥扫描，及执行方案所列的本 PR 验收。业务 PR 还须运行真实走查。PR 仅改验收制度、文档和工作流的，使用配置专项检验，验证工作流已撤下并运行相同的自动化检查。
4. 全部通过才向 GitHub 推送测过的最终提交并创建 PR，附上脱敏结果、最终提交、所测 `main` 和合并树编号。独立复审有改动时，按新的完整组合重新验收。
5. 所有合并人在本机同一工作区运行 `scripts/merge-vm-pr.mjs`。脚本持有 Git 公共目录中的一把锁，在锁内核对复审的必跑专项清单、远端 `main`、PR 头和虚拟机验收报告，再以 GitHub 的 squash PR 方式合并。它校验合并提交的父提交、代码树及该提交是否进入远端 `main`。输入变化就重验。当前私有仓库套餐暂无服务端分支保护，所以团队需要共同使用本机入口来串行合并。

```bash
# 以下命令在验收虚拟机中执行
node /home/verifier/acceptance-vm.mjs \
  --bundle /home/verifier/cert-board-input.bundle \
  --base "$BASE_SHA" --head "$HEAD_SHA" \
  --acceptance docs:html --config-only
```

业务 PR 使用 `--model-profile /已授权的客体配置文件` 运行同一命令，按 PR 增加多个 `--acceptance <pnpm-脚本>`。专项必须在根 `package.json` 登记，报告记录实际脚本名。真实模型及 L08 选中后，明确跳过视为未通过。授权模型配置在业务专项之前加载。真实走查使用 VM 自己的代理、开发数据库和浏览器。模型配置只包含现有授权的 OpenRouter 凭据、Cursor 专用配置路径和经确认的隐私标志。审批依旧从浏览器完成。使用合成资料验证外部核实通道。凭据、登录状态、详细日志和真实截图保存在本机控制的位置。虚拟机上 `report.json` 只包含状态、步骤与版本，PR 摘要不含正文和密钥。

独立复审通过后，在 Windows 仓库工作区执行。每条必跑专项分别传 `--acceptance`。PR 说明已经复审确认无专项时使用 `--no-special-checks`。配置 PR 必跑 `docs:html`。

```powershell
node scripts/merge-vm-pr.mjs --pr $prNumber --report $reportPath --reviewed-head $reviewedSha --subject $mergeTitle --acceptance docs:html
```

合并入口中断留下锁时，先用 `git rev-parse --path-format=absolute --git-common-dir` 找到锁目录 `cert-board-vm-merge.lock`，读取其中 `owner.json` 的 PR、进程编号和时间。核对记录的进程及其启动时间。确认进程已经退出、没有仍在执行的合并，再查 GitHub 上该 PR 和远端 `main`，确认合并是否已经完成。只有确认锁残留时才删除该 `owner.json` 和空锁目录。锁记录缺失时也先核对本机合并进程及远端状态。
