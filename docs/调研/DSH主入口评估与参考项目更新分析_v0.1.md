# DSH主入口评估与参考项目更新分析

文档版本：v0.1

编制日期：2026-11-17

文档状态：草稿，供技术负责人和管理层讨论

适用对象：Lan、组长、管理层

本文回答两个问题：一，选DSH做主对话入口、把DSH改造成认证板块的工作台是否合适；二，参考项目（AiNativeCrm）的新版源码有哪些更新对我们有价值。依据是DSH官方文档（GitHub `deepseek-ai/deepseek-harness`，2026-11-17读取）、组长仓库 `docs/12-Harness本地试验/` 的试验记录，以及新旧两版参考项目的逐文件对比。

## 0 结论

1. **可以选DSH做主入口，但不要改造DSH本身。** 正确的做法是在DSH上做插件：DSH负责对话界面和交互；认证板块的执行约束、业务数据、审批、预算、评测和定时任务放在我们自己的后端（总体方案的路线C）。DSH处在快速变化的预览阶段，复制它的源码再修改，等于自己维护一个快速变化的产品。
2. **选DSH有五个前提**：
   - 管理层书面接受它是预览版软件；
   - 关闭它默认的数据上传和高风险工具；
   - 用认证网关解决多人使用；
   - 后台执行不放在DSH里；
   - 先用3–5天做一次专项验证。

   详见第2章。
3. **组长已经做过的DSH接入可以复用。** 包括登录网关、每人独立运行、业务工具插件、确认卡片、重启后恢复等，都有真实运行记录。如果选DSH，应当和组长合作，复用这部分成果。
4. **参考项目的更新有5项值得吸收**：Pi升级到1.3.0、专职AI意见冲突时停止写入、业务语义层、事实的有效期与修订、任务方向可改且可暂停外发。前两项影响总体方案和需求，其余进入需求V0.7和技术方案。详见第3章。

## 1 DSH是什么

DSH（DeepSeek Harness）是DeepSeek开源的Agent工作环境，MIT许可。以下事实来自官方文档：

| 方面 | 事实 |
|---|---|
| 架构 | 「一切皆插件」：模型接入、工具注册、会话日志，以及Agent循环本身都是插件，可以通过配置替换 |
| 扩展方式 | 可以注册工具、为不同会话配置不同的工具集、在对话中注册自定义展示节点（如审核卡）、目标跟踪、后台任务、由外部Webhook触发会话、子Agent、自定义会话存储等 |
| 运行形态 | 网页界面（默认端口3080）、桌面应用、命令行、SDK |
| 默认工具 | 文件编辑、命令行、网页搜索、网页抓取、子Agent、任务与目标跟踪；文件写入限制在工作区内，高风险操作前询问 |
| 状态 | 官方安全说明原文：「experimental developer-preview software. It has not undergone a security audit and must not be treated as secure or production-ready.」（实验性开发者预览软件，未经安全审计，不得视为安全或可用于生产）；README注明会有破坏兼容性的变更 |
| 版本 | npm最新发布版0.2.2-rc.1，要求Node 24.9以上 |

需要特别注意的默认行为：

1. **会话日志上传。** 默认开启的「DeepSeek会话日志」插件，在使用DeepSeek官方接口时，每次请求都附带会话日志，单次最多8 MiB，内容包括对话和工具结果。关闭方法是把该插件设为 `enabled: false`，或在网页设置中关闭对应开关。
2. **反馈时上传。** 会话遥测默认为「仅反馈」：用户给出评分、修改等反馈时，会上传截至当时的完整对话及上下文。设为 `DISABLED` 才完全关闭。
3. **网页抓取。** 网页抓取工具默认不需要逐次批准，并且可以访问本机和内网地址。
4. **网页访问认证。** 网页服务默认只监听本机；对外提供时放在反向代理后面。认证方式是启动时打印的一次性链接换取会话Cookie，官方说明原文为「The printed URL carries a process credential, so share it only with intended users.」（打印出来的链接带有进程凭据，只能分享给预期的用户）。也就是说，一个DSH进程只有一个使用者身份，没有内置的多用户账号和角色。

## 2 选DSH做主入口的评估

### 2.1 为什么可以选

1. **形态吻合。** 管理层要的是「在板块里和AI对话」，DSH本身就是对话优先的Agent环境，扩展点覆盖了我们需要的大部分能力：工具、审核卡、目标、后台任务、外部事件触发、子Agent。
2. **组长已经验证了很多。** 组长的试验记录显示（`04-开发状态.md`）：
   - 业务登录后进入真实的DSH 0.2.2-rc.1；
   - 六个工坊的原生对话调用受控业务工具，结果写入独立数据库；
   - 登录和注销连续9次都能启动真实DSH、撤销权限、停止专属容器；
   - 重启后对话、任务和动作编号保持不变，不会重放；
   - 确认卡片能在DSH中显示和操作。
3. **公司已在使用。** 本机已安装并在使用DSH桌面版。

### 2.2 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 预览版软件 | 官方明确说不能视为安全或可用于生产，会有不兼容变更。需求NF09要求按风险验证AI工具，每次升级DSH都要重新验证 | 管理层书面接受风险；固定版本，升级前跑回归；业务逻辑不放在DSH里，降低升级影响 |
| 默认外发 | 会话日志上传、反馈上传默认开启，与我们的数据边界（需求V0.6第5.5节）冲突。组长试验中也发生过一次模板结构进入模型上下文的事件，按已外发处理 | 我们的配置中关闭上传和遥测；内部资料只用本地模型；上线前用抓包确认没有外发 |
| 高风险默认工具 | 命令行、文件编辑、能访问内网的网页抓取，对认证板块没有用处 | 自定义配置，只保留我们的业务工具；关闭命令行、文件写入、网页抓取 |
| 多人使用 | 没有内置的多用户账号和角色，一个进程对应一个使用者 | 沿用组长的做法：认证网关加每人独立的DSH容器；共享的业务状态放在我们的后端 |
| 后台执行 | 定时提醒、法规监测、目标唤醒需要在没人对话时运行，不适合放在每人一个的对话进程里 | 后台执行由我们的后端完成，结果通过DSH会话或企业微信通知人 |
| 修改DSH源码 | DSH变化很快，复制后修改等于长期维护一个分叉 | 只用插件和配置扩展，不修改DSH源码 |

### 2.3 建议的做法

```
人 ──> DSH（固定版本、收紧后的配置）
        │  认证板块插件：业务工具、审核卡、板块AI的配置
        ▼
     认证板块后端（路线C）
        动作级别与审批、目标与运行、预算、确定性检查、评测、定时任务、业务数据
        │
        ├─> 模型网关 ─> 本地模型 / 外部模型（按数据级别）
        └─> 企业微信提醒
```

要点：

1. **约束放在后端，不放在前台。** 动作级别、审批、预算、数据边界在后端的工具服务中执行。无论是DSH还是将来的其他入口调用，规则都一样。这样DSH以后如果要换，板块本身不用重写。
2. **审核卡用DSH的自定义对话节点实现。** 按钮调用后端接口完成审批，审批记录以后端为准。证据较多时（PDF原页），卡片链接到后端提供的证据查看页。
3. **后台执行在后端运行。** 定时任务、唤醒、长时间的目标由后端执行；需要人处理时，在DSH中出现待办或审核卡，同时发企业微信提醒。
4. **对话中的板块AI由哪个Agent循环驱动，在专项验证中确定。** 一种是用DSH自己的Agent循环调用我们的工具；另一种是DSH把对话交给我们后端的板块AI（DSH支持把一个回合委托给其他产品）。前者简单，后者能保证前台和后台使用同一套执行逻辑。

### 2.4 专项验证（建议3–5天）

| 编号 | 验证内容 | 通过标准 |
|---|---|---|
| DV-01 | 收紧后的配置：去掉命令行、文件写入、网页抓取，只保留业务工具 | 板块AI看不到也调用不了被去掉的工具 |
| DV-02 | 关闭会话日志上传和遥测 | 抓包确认没有发往DeepSeek或其他外部地址的请求 |
| DV-03 | 接入本地或OpenRouter的OpenAI兼容模型 | 工具调用正常，复用RV-02的检查 |
| DV-04 | 审核卡作为自定义对话节点，按钮调用后端审批 | 审批几天后再做也有效；重启后卡片状态正确 |
| DV-05 | 多人：认证网关加每人独立容器（复用组长方案） | 两个用户互相看不到对方的会话和资料 |
| DV-06 | 后端发起的后台运行结果出现在用户的DSH中 | 用户打开DSH能看到待办，并能直接处理 |

DV-01、DV-02任一不通过，不建议用DSH处理内部资料。

### 2.5 对总体方案的影响

- 待决事项D01改为「主入口用DSH（插件方式），提醒用企业微信」，待管理层书面确认，并确认接受预览版风险。
- 路线C不变。可运行切片中「自建对话入口」换成「DSH插件和后端接口」，另加专项验证和收紧配置的工作，总工作量大致相当。
- 如果和组长合作，组长的 `integrations/harness/`（认证网关、运行容器、插件构建）可以作为DSH接入的起点。组长仓库的其余部分按原约定不再推进。

## 3 参考项目的更新

### 3.1 更新概况

新版（`New AiNativeCrm-main.zip`，解压在 `reference/new/`）与本机原有版本相比：

- 新增230个文件，修改115个，删除1个；
- 新增6个数据库迁移，时间为2026-11-12至11-14；
- 依赖升级：Pi两个包从0.86.1升到1.3.0，Next.js 16.4.2，Sentry 11。

默认向作者社区Sentry发送错误报告的设置仍然存在，借鉴代码时仍需关闭。

### 3.2 对我们有价值的更新

| 更新 | 内容 | 对我们 | 去向 |
|---|---|---|---|
| Pi升级到1.3.0 | Pi Agent Core进入1.x；接口有不兼容变化，例如每轮结束后判断是否停止的钩子由 `shouldStopAfterTurn` 改为 `finishTurn` | 总体方案中「Pi仍是0.x」的风险降低；我们直接基于1.3.x开发，RV-02的验证脚本需按新接口调整后重跑 | 总体方案、技术方案 |
| 专职AI意见冲突时停止写入 | 只读专职AI对同一字段的证据不一致，或读取的来源版本不同时，主责AI停止写入，标记为未解决，并请人确认 | 我们的一致性检查（R09）和变更评估（M07）都用专职AI，必须有这条规则 | 需求V0.7第6.2节 |
| 业务语义层（Ontology Lite） | 概念目录带版本；先判断问题能不能回答，并列出缺失的定义；只执行审阅过的查询，结果标为完整、部分或无法回答，并附回执；查询使用只读数据库角色，有行数和时间限制 | 适合主数据查询（M01）和指标（S04），例如「哪些证照90天内到期」要按审阅过的口径回答。字段的单位在概念目录中定义，可以减少RV-01那种把「分」当「元」的错误 | 需求V0.7第5章、技术方案 |
| 事实的有效期与修订 | 确认过的事实可以带有效期、锁定和修订记录；AI从结束的会话中提出事实候选并附证据片段，不自动确认；人可以确认、改写或拒绝；冲突由负责人裁决 | 对应需求V0.6第5.2节「人确认的事实」和「待核实信息」：证照事实有有效期，AI从资料中提出事实候选 | 需求V0.7第5.2节 |
| 任务方向可改、外发可暂停 | 负责人可以保存新的任务方向，旧方向不再进入模型上下文；可以暂停和恢复对外发送，暂停期间已批准未发出的消息不发；恢复后不自动重发旧的审批 | 对应目标与运行（2.5）和对外动作（2.4）的细化 | 需求V0.7第2.4、2.5节 |
| 评测规则细化 | 「没读取」不能当作「不存在」；「没有测量」不能当作「得分低」；读取评测失败时保留运行结果，只重试读取 | 一致性检查同样适用：没检查过的文件不能报告为「没有问题」 | 需求V0.7第8.2节 |
| 恢复时使用当前发布的版本 | 运行恢复时，用当前发布的组织记忆替换旧的系统指令 | 我们需要决定：审批后续跑时规则包已更新，用旧版还是新版，并记录所用版本 | 技术方案 |
| AI驱动的验证技能（`verify-crm`） | 让AI按固定步骤启动本地环境、操作浏览器、收集证据、清理环境，覆盖运行、审批与撤回、外发控制、专职协作、评测 | 可以用作我们软件验证（需求NF09）的证据收集方式；它的启动步骤（移开迁移、导入基线）与我们RV-01的做法一致 | 技术方案、软件验证计划 |
| 对话工作台改进 | 输入框始终可见、面板可用键盘操作、状态变化有提示 | 界面参考 | 技术方案 |

### 3.3 对我们没有价值的更新

日程时区、标签筛选、广告活动名称、西班牙语翻译、邮件设置、扩展管理、OpenCode接口等CRM业务和界面的改动。可选接入的Mem0（记忆）、WeKnora（知识库）、Langfuse（运行观测）默认全部关闭，是否作为我们的组件候选在技术方案中再评估，前提是都能在内网部署。

### 3.4 对已有结论的核对

新版修正了一个预算重复计算的问题。这个问题与升级Pi 1.0后用量的上报方式有关。验证报告RV-01第1次运行用的是旧版，当时每轮记录的是该次调用自身的用量，合计33,424个token，与模型调用日志的汇总（输入8,185、缓存读取24,320、输出919）一致。因此那次超出预算是真实用量，验证报告的结论不需要修改。这里只核对了用量数字，没有逐行核对旧版的预算代码。
