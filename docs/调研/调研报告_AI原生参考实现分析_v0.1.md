# 调研报告：AI原生参考实现分析（AiNativeCrm）

文档版本：v0.1

编制日期：2026年11月17日

文档状态：草稿

适用对象：本项目负责人、开发人员

本报告分析一个已授权使用的AI原生全栈项目（AiNativeCrm），说明它如何实现「AI在后台执行业务、人在关键点监督」，并逐项判断这些做法对器械认证板块是直接采用、修改后采用还是不用。结论用于更新需求文档V0.6和编写总体方案。

## 0 结论

1. **方向得到印证。** 参考项目与需求V0.5的核心理念一致：AI是执行者而不是建议框；业务事实以数据库为准；AI的动作按风险分级；改进必须经人批准才生效；运行结束不等于业务完成。
2. **补齐了V0.5的实现机制。** 参考项目把这些理念落成了可运行的机制：目标（Mission）与单次运行分离、四级工具分级且未登记工具一律拒绝、提案—审批—续跑、对外动作的草稿与最终闸门、知识策略、确定性优先的评测、预算上限、通过即时通讯向同事要资料并自动续跑。V0.6应吸收这些机制。
3. **有两处不能照搬。** 一是业务差异大：我们面对监管机构和大量PDF、扫描件、加密eSTAR，单个任务周期以月计，对外提交永远由人完成。二是「自主权随表现提升」在参考项目中只写在愿景里，代码中只有人工切换的辅助/自动模式，我们需要自己设计等级晋降机制。
4. **出现一条新的技术路线。** 作者授权无条件使用，且三方（参考项目、组长仓库、四板斧培训）都使用Pi Agent内核，因此「以参考项目的运行内核为底座，替换为认证业务」成为可选路线，需在总体方案中与其他路线对比后决定。

## 2 总体架构

```
自然语言任务 + 业务对象
        │
        ▼
上下文构建：业务记录 · 知识库 · 记忆 · Skills · 历史运行
        │
        ▼
Pi Agent 循环 ◄──────────── 工具结果 / 人工确认
        │                          ▲
        ▼                          │
Harness：权限 · 范围 · 策略 · 预算 · 审批 · 恢复
        │                          │
        ▼                          │
工具端口 ───────► 业务操作 ───────► 观察结果
        │
        ▼
业务状态变化 + 运行事件 + 追踪 + 评测
```

分层职责：

| 层 | 职责 |
|---|---|
| 业务数据库 | 业务事实的唯一来源 |
| 运行记录 | 每次执行的状态、事件、检查点；与业务事实分开存放 |
| Pi Agent 循环 | 只负责推理和决定调用哪个工具，类型封装在适配层，业务层不直接依赖 |
| Harness | 决定每个工具调用是直接执行、自动执行并可撤销，还是落成待审提案 |
| 知识与记忆 | 提供依据，带来源版本和定位 |
| 评测 | 对每次运行打分，结果存档 |

## 3 关键机制与采用判断

判断分三种：**采用**（原样采用设计）、**修改后采用**（采用思路，按我们的业务调整）、**不用**。

### 3.1 目标与单次运行分离

- **它怎么做**：`ai_workbench_runs` 记录一次执行，`ai_missions` 记录持续的业务目标，保存目标、验收条件、截止时间、最多运行次数（默认4次）和跨运行的预算。运行完成后目标进入「待复核」，原因是「业务结果未核实」，只有负责人确认后才算完成。目标有等待客户、等待内部同事、待复核等状态；客户回复、同事补充、负责人补充方向三种事件可以唤醒目标，新建一次运行继续执行。同一事件不能唤醒两次；无法判断归属时转人工复核，不猜测。
- **关键文件**：`docs/architecture/mission-state.md`；`lib/ai/agents/mission-*.ts`；表 `ai_missions`、`ai_mission_events`、`ai_mission_wakes`。
- **落地**：已实现。项目明确说明「业务结果已核实」字段始终为假，自由文本验收无法由程序证明。
- **判断：修改后采用。** 一个注册项目持续数月，等待对象更多：等FDA或加拿大卫生部、等实验室报告、等研发资料、等代理人、等管理层决定。我们需要更多等待状态和唤醒事件（来函、报告到达、资料到达、到期），以及「AI任务完成」与「拿到许可」的明确区分。对应V0.5第2.5节。

### 3.2 工具效果分级，未登记一律拒绝

- **它怎么做**：每个工具标为读取、可撤销写入、对外动作、不可逆动作四级之一。默认所有写入按不可逆处理，只有登记了补偿方法的才算可撤销；发送消息、转人工、向同事提问都是对外动作。目录中查不到的工具不交给模型，批准时也拒绝执行。只读模式在两处拦截写入。
- **关键文件**：`lib/agent-runtime/types.ts`（`ToolEffect`）、`lib/ai/agents/tool-effects.ts`、`lib/mcp/tools/catalogo/`。
- **落地**：已实现。
- **判断：采用。** V0.5第2.4节的动作分类改为这四级，并增加「未登记工具一律拒绝」「默认按不可逆处理」两条规则。

### 3.3 可撤销写入

- **它怎么做**：只有少数字段的修改允许AI自动执行。执行前读取当前值作为快照，写入时带版本号防止覆盖他人修改，同时保存把值改回去的补偿参数；负责人可以一键撤销，撤销同样校验版本号，后来的人工修改不会被静默覆盖。无法生成补偿参数时不执行，改为提案。
- **关键文件**：`lib/ai/agents/reversible-lead-update.ts`；表 `ai_agent_action_proposals.compensation_args`。
- **落地**：已实现，项目注明补偿不等于跨进程原子回滚，进程中断时需按现状人工对账。
- **判断：修改后采用。** 我们的运营字段（备注、提醒状态、草稿、节点进度）可以用这种方式自动写；真值字段（证照号、到期日、授权状态、获准事实）始终走审核。

### 3.4 提案、审批与续跑

- **它怎么做**：需要人决定的动作写成持久化的提案，运行进入「等待确认」。人批准或拒绝后，结果作为观察写回保存好的AI对话状态，从断点继续执行，不重跑原任务。批准先记录「已批准、待执行」，再执行工具；结果不确定时不自动重放，标为需对账。
- **关键文件**：`lib/ai/agents/approved-workbench-tool.ts`、`workbench-resume-job.ts`、`workbench-reject-decision.ts`；表 `ai_agent_run_states`。
- **落地**：已实现。
- **判断：采用。** 对应V0.5第3.4节审核卡：审核通过后AI自动接着执行后续步骤，人不需要再发指令。

### 3.5 对外动作：草稿加最终闸门

- **它怎么做**：模型不能直接对外发送。发给客户的消息先存为草稿并绑定到具体运行和提案；批准只表示进入发送队列；真正发送前，发送进程再检查一次退订、任务是否已停止、是否已暂停发送。负责人可以暂停发送，暂停后已批准但未发出的消息作废。已经进入渠道的消息无法撤回，只能对账。
- **关键文件**：`fn_reply_action`、`fn_reply_context_current`、`fn_reply_delivery_policy`；表 `ai_reply_drafts`。
- **落地**：已实现。
- **判断：修改后采用。** 我们的对外动作分两类：向监管机构提交和缴费永远由人在官方系统完成，不进入自动发送；向CRO、实验室、代理发询价和催办可以走「草稿—批准—发送前再检查」这条路。

### 3.6 交还人工

- **它怎么做**：转人工时同时关闭三把锁（标记由人处理、AI静默、指派给人），任何一把都会让AI的回合直接跳过；交还AI时三把锁一起放开。人的处理决定追加进下一回合本来就会读取的上下文摘要，而不是另建一张只有交接代码才读的表。
- **关键文件**：`lib/agent-engine/agent/human-handoff.ts`、`lib/escalacao/retomada.ts`；`docs/architecture/escalacao-ciclo-humano.architecture.json`。
- **落地**：已实现。
- **判断：修改后采用。** 当注册人员说「这件事我来处理」时，AI停止该事项的自动执行；人处理完交还时，AI读取人的处理结果继续。

### 3.7 多Agent：主管加只读专职

- **它怎么做**：主管Agent按固定的协作计划并行启动3个只读专职Agent，各自调查一个方面，共享父运行的预算；数据库约束专职Agent只能只读，写入和对外动作只属于父运行。项目明确不做通用Agent图，批量筛选用数据库查询加Agent分析短名单。
- **关键文件**：`lib/ai/agents/collaboration-runtime.ts`、`collaboration.ts`；`docs/architecture/agent-crm-workbench.md`。
- **落地**：已实现，真实模型运行记录评分87/100。
- **判断：修改后采用。** 适合一致性检查（按资料类别并行抽取）和变更影响评估（按市场并行判断），由一个主责能力汇总并写入。

### 3.8 运行可靠性

- **它怎么做**：队列任务只带运行编号；执行前核对租约，租约过期的进程不能再写；取消通过中止信号传到模型调用；事件按序号先落库，刷新后可从断点回放；专职Agent用执行令牌防止过期进程收尾。
- **关键文件**：`lib/ai/agents/workbench-job-lease.ts`；表 `ai_agent_run_events`、`job_queue`。
- **落地**：已实现。
- **判断：采用。** 对应V0.5的NF04。

### 3.9 知识策略与证据定位

- **它怎么做**：每个Agent配一份知识策略，由Harness执行而不是只写在提示词里：允许查哪些资料空间、是否必须先检索、引用规则、最少证据数、缺资料时的行为（交部分结果、报告缺失、整个运行失败）。每条证据带稳定定位（来源、版本、地址），检索后再核对来源版本；知识库为空时明确显示为空，不编造证据。
- **关键文件**：`lib/ai/knowledge/contracts.ts`、`lib/ai/agents/builtins.ts`。
- **落地**：已实现。
- **判断：采用。** 为29项能力各配一份知识策略；与V0.5的V1引语逐字匹配互补。

### 3.10 记忆分层

- **它怎么做**：组织记忆按版本发布，指针指向当前版本；客户事实必须经人确认，带内容哈希，只在当前会话范围内可读；Skills按不可变版本保存，提示词里只放名称和描述，匹配时才注入正文。
- **关键文件**：表 `org_memory_versions`、`org_memory_pointers`、`ai_customer_memories`、`skill_versions`、`skill_pointers`；`lib/agent-engine/agent/skills.ts`。
- **落地**：已实现。
- **判断：修改后采用。** 对应关系：市场规则包 → 版本化Skills；产品合规主数据中的获准事实 → 人确认的事实；公司模板和工作方式 → 组织记忆；案例库 → 知识库。

### 3.11 结构化结果

- **它怎么做**：专职Agent除文字摘要外，提交结构化陈述：主语、谓词、值、置信度和证据定位。评测可以区分「只写了一段话」和「提交了可审计的事实」。
- **关键文件**：`lib/ai/agents/evidence-claims.ts`；`docs/architecture/workbench-structured-result.md`。
- **落地**：已实现。
- **判断：采用。** 一致性检查的差异项、路径研判的候选、变更评估的判断都用结构化陈述交付，便于程序校验和生成审核卡。

### 3.12 评测

- **它怎么做**：七个维度：任务完成、回答质量、依据充分、工具可靠、策略遵守、效率、协作质量。先做确定性检查（工具事件是否成对、只读模式是否有写入、对外动作是否在人工确认之后、结论证据是否出现在成功的工具结果里）。可选的语义评审只能降分、不能升分，评审失败时把「通过」降为「待复核」。评测报告按运行、评测方案版本和输入指纹存档，同一材料重放得到同一结果。回归语料锁定评测函数的行为。
- **关键文件**：`lib/ai/evals/contracts.ts`、`evaluate-run.ts`、`semantic-judge.ts`、`profiles.ts`；表 `ai_agent_eval_reports`。
- **落地**：已实现；评测不拦截发布，也不改变自主模式。
- **判断：采用，并加强。** 维度和合成规则写入V0.6第8章；我们另外要求评测结果用于等级晋降（参考项目没有做）。

### 3.13 自我改进

- **它怎么做**：定时任务对已完成的回合做评审，评审不通过时生成一条改进提案（追加到某个Agent的规则或组织记忆）。只有管理员点击「应用」才生效：复制当前版本、追加一段、发布新版本，不改写整份提示词；已应用的提案不能重复应用。运行中的「差一点命中」写成待人工策展的候选样例，不自动变成测试或技能。人工改稿只作为同一会话后续草稿的参考，不升格为全局规则。已解决的对话要有人标记「可用于知识库」才会匿名化后入库。
- **关键文件**：`lib/agent-engine/flywheel/live.ts`、`lib/ai/apply-proposal.ts`、`lib/agent-engine/golden-candidates/`；表 `flywheel_judge_verdicts`、`flywheel_distiller_proposals`。
- **落地**：评审到提案到人工应用已实现，目前只评一个维度；用业务结果驱动改进、以转人工作为缺口信号，只在文档中。
- **判断：修改后采用。** 与V0.5第2.5节一致。补充三条：改进以追加版本的方式生效，可回退；候选样例与正式评测集分开管理；人工修改和退回原因按能力归类，作为改进提案的主要来源。

### 3.14 预算上限

- **它怎么做**：每个组织设月度上限、告警阈值和宽限期；默认不阻断。达到上限时第一次只警告，之后在请求发出前拒绝，并把进行中的事项交回人工；调高上限不会自动恢复已暂停的事项。测不到价格时明确标为「计量不完整」。
- **关键文件**：`lib/agent-engine/edge/llm/orcamento.ts`、`run-model-call.ts`；`docs/architecture/teto-de-orcamento.architecture.json`。
- **落地**：已实现。
- **判断：采用。** 补入V0.6非功能要求；目标级的累计预算（3.1）一并采用。

### 3.15 通过即时通讯与同事协作

- **它怎么做**：同事的飞书账号与系统账号通过一次性口令绑定，消息正文、群名、@都不能自报身份。AI向同事提问先成为提案，负责人批准后才发出；发出后用真实消息编号绑定回复线程。同事回复后验签、解密、入队，在目标的行锁内复核身份，新建一次运行继续执行；同一事件只生成一次运行。同事提供的信息作为未经核实的事实使用，执行身份仍是任务负责人。飞书文本不构成任何审批。
- **关键文件**：`docs/architecture/internal-collaboration-feishu.md`；表 `ai_internal_platform_users`、`ai_mission_internal_threads`、`ai_internal_question_outbox`、`ai_internal_event_inbox`。
- **落地**：代码已实现；真实租户安装和端到端联调尚未完成；企业微信未接入。
- **判断：修改后采用。** 对应V0.5第3.7节「资料提供方不需要登录系统」。我们的协作对象除内部同事外还有CRO、实验室、代理，渠道可能是飞书、企业微信或邮件（D01、D03）。「即时通讯文本不是审批」这条原样采用。

### 3.16 自主模式

- **它怎么做**：每个Agent有人工设置的「辅助」或「自动」模式；工作台每次运行有「只读调查」或「行动」两种模式。愿景文档写有「自主权随治理证明Agent做对而提升」，但代码中没有等级、阈值或自动晋级。
- **判断：不能照搬，需要自行设计。** V0.5第2.3节的三级分工和晋降规则保留，V0.6补充：晋级由评测和试点数据支持，经管理层批准；降级可自动触发。

### 3.17 隐私与事件

- **它怎么做**：运行事件按字段白名单保存，不含消息正文、原始工具参数和凭据；模型的对话状态放在只有服务端可读的表中；内部协作的正文加密保存，处理后清除。
- **判断：采用。** 我们的资料是公司内部和保密资料，审计事件只记对象编号和状态，正文留在资料库内。

### 3.18 对话优先的工作台

- **它怎么做**：工作台以对话为主，任务结果在对话中呈现；待审提案在对话中出现操作入口；运行详情（提案、目标状态、用量、专职Agent、评测、完整事件）放在可打开的侧边面板中。
- **判断：修改后采用。** 与管理层「过程尽量少看」一致：默认只显示结果、依据和需要人做的事；详情面板收起，需要时展开。

## 7 对总体方案的输入

### 7.1 技术路线候选

| 路线 | 做法 | 优点 | 代价与风险 |
|---|---|---|---|
| A 以参考项目为底座 | 保留其Agent内核、Harness、目标、协作、评测、预算；去掉CRM业务和WhatsApp等渠道；新增认证业务记录、文档解析、市场规则包 | 最成熟的执行机制可直接用；作者授权；规模大、测试多 | 代码量大（约6000文件），需先裁剪；基于Next.js和Supabase，内网部署要评估；葡萄牙语和中文混杂的代码与文档 |
| B 复用组长后端，新增Harness | 在组长的Fastify、PostgreSQL、Python文档服务和认证线台账上，按参考项目的设计新增Agent循环和Harness | 认证业务字段、台账、清单模板和评测已在代码中 | 组长项目已被否决，代码是围绕页面和台账设计的；Harness要重写 |
| C 新建，只借鉴设计 | 新建精简项目，按本报告的机制和V0.6需求实现 | 结构最贴合AI原生和认证业务 | 开发量最大；机制要重新验证 |

选型应依据：能否在公司内网部署；能否接入选定的模型（本地Muse-Spark或千问）；能否接入选定的对话载体；文档处理能力；团队维护成本。建议在总体方案中先做两项验证（见第8章）再决定。

### 7.2 其他需要在总体方案中确定的事项

- 对话载体：公司在用的Harness/DSH、飞书、企业微信或网页（V0.5 D01）。参考项目已有飞书协作实现。
- 模型：Pi AI支持OpenAI兼容接口，本地Muse-Spark和千问国际版都可以按兼容接口接入，需实测工具调用能力。
- 资料接入：WPS、邮件；文档解析沿用T1的流水线。
- 正式记录与签字：继续纸签或启用电子签名。
