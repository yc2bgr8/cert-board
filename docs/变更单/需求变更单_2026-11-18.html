1 变更内容

1.1 不区分角色

  1. 登录本平台的都是注册部门的成员，登录后不区分角色：每个人都可以发起和处理注册项目与维护事项，都可以审核Agent的结果。界面上只显示人名，不显示「注册人员A」「注册人员B」之类的角色。
  2. 每个注册项目和维护事项仍有一位负责人：接收提醒，事项出现在他的「待我处理」中；负责人可以更换。其他成员同样可以查看和审核。
  3. 取消以下强制规则：「每项工作只设一名主责，另一名注册人员复核，主责与复核不能是同一人」（需求2.1），以及各能力中「注册A审核、注册B交叉检查」一类的分工。需要同事复核时，在审核卡上「转交他人」。质量体系是否要求申报资料由第二人复核，请质量负责人确认（D22）；确认需要时，再加为可配置的规则。
  4. 销售人员和管理层不登录：
    • 销售的合规报告、证照资料包、UPC请求，由注册人员在对话中代为提出（以后可以经邮件转入，需求5.7）。取消销售视图和「销售只能看到自己的请求」的要求。
    • 管理层的周报和决策项由Agent准备，经企业微信或邮件发给管理层（S04，按内部消息的规则发送）；管理层的决定由注册人员记录到对应的项目中。
  5. 系统维护（用户、模型配置、预算、任务监控）是个别人员的管理权限，不是业务角色。有这项权限的人在设置中看到维护页入口（原「技术维护人员」，需求NF14）。
  6. 资料提供方不变：不登录，接收Agent的资料请求和催办（需求3.7）。
  7. 各文档中把「注册人员A」「注册人员B」「注册A」「注册B」作为执行人、审核人或确认人的地方，一律理解为「注册人员」，即任何一位部门成员，或该事项的负责人。

1.2 两个Agent：注册Agent和维护Agent

首版就分为两个角色Agent，取代「首版只有一个器械认证Agent」（需求2.1「角色Agent」一段）：

Agent负责切片中的能力
注册Agent注册项目：R01–R12R09 申报一致性检查
维护Agent维护事项：M01–M12；S01 合规报告与证照资料包、S02 UPC（都依赖证照台账）；S04 周报与管理层决策项M02 美国注册与列名核查

规则：

  1. 两个Agent共用同一个内核、同一套工具和约束、同一套预算和计量、同一个资料库和项目工作区机制；各自有系统提示词、技能索引和评测集（即两份Agent定义，技术方案4.4）。
  2. 注册项目下的对话用注册Agent，维护事项下的对话用维护Agent；「新对话」由人选择，默认注册Agent。唤醒时按目标所属项目的类型选择Agent。
  3. S03（沟通与会议归档）由所属项目的Agent处理；S05（AI工作质量保障）是系统功能，不属于某个Agent。
  4. 两个Agent都可以读取台账回答问题（台账问答，需求5.6）。
  5. 交接：R12获证后，注册Agent建立对应的维护事项并附移交清单（按当前对话的权限模式执行），之后由维护Agent负责。
  6. 以后需要更多角色Agent时，按同样方式增加Agent定义。

1.3 权限模式

每个对话有一个权限模式，在输入框旁选择，可以随时切换，从下一次工具调用起生效。新对话默认「请求批准」。

模式Agent直接做的先请人批准的
只读读资料和记录、检索、运行检查、计算、回答问题不做任何写入，工作副本也不能写（即原「只查不动」）
请求批准（默认）只读模式的全部；在本对话的工作副本中写、改文件；在沙箱中运行代码；启动子Agent；维护计划；保存工作区版本；把附件和产出导入资料库写业务记录（台账字段、AI建议、提醒、建立项目）；给内部同事发消息；作关键判断（1.4）前先提出建议，等人确认
完全允许请求批准模式下直接做的全部，加上：写业务记录；给公司内部同事发资料请求和催办；关键判断由Agent作出，写明依据后继续中途不需要批准，只在最后把结果交人审核

任何模式下都不变的：

  1. 结果交人审核。 交付物以审核卡提交，人通过后才算完成；定稿冻结只在人批准后发生（需求2.6）。
  2. 发往公司外部的消息每条都要人批准。 收件人是CRO、实验室、代理、客户等公司外部对象的，先生成外发提案，人批准后进入外发队列，发送前再检查（需求2.4、3.4）。
  3. 法律和质量体系效力的动作只能由人完成。 监管门户提交、缴费、签署、向监管机构或客户发正式文件由人完成；不可逆动作始终拒绝；真值字段只由人写。
  4. 安全边界不变。 数据级别路由、密钥、沙箱不联网、出网白名单、预算上限、审计记录和撤销都照旧。权限模式只决定「问不问人」，不放宽这些边界。
  5. 批准只能在浏览器界面中点击。 在对话或企业微信中说「同意」不算批准（需求3.4规则4、IX-08）。
  6. 工具目录按模式生成。 只读模式下写入工具不出现在目录中（需求2.4规则3）。

批准请求的形式：输入框上方出现一张小卡片，写明Agent要做什么、改哪条记录（改前和改后的值），或消息的收件人和内容；按钮为「允许」「本对话中都允许」（同一个工具在本对话内以后不再问）和「拒绝」（可以写原因）。拒绝时Agent收到原因并调整做法。批准请求只能由发起该对话的人处理。

完全允许模式下直接发送内部消息时：收件人必须是已登记并绑定身份的公司同事（需求3.7规则1）；发送前照常检查事项是否已取消、外发是否已暂停、附件的数据级别是否允许；同一事项对同一个人每个工作日最多催办一次；发出的消息在对话中显示，并进入日摘要。

1.4 过程由Agent完成，人审核最终结果

  1. 需求2.2第2条改为：人负责目标和最终结果。 分类与路径、对比器械、法规适用性、变更是否需申报、发补答复立场等判断，在过程中由Agent作出（请求批准模式下先提出建议、等人确认），写明理由、备选方案和依据，并在最终的审核卡中逐条列出。人不同意时在对话中说明，Agent修改后重新提交。
  2. 仍由人决定的：风险接受；超出预算的费用；向监管机构或客户发出正式文件前的最终确认；需要管理层决定的路径、重大风险、大额费用和关键商业结论。
  3. 缺事实和证据冲突时仍要问人。 资料中没有的信息（收件人、日期、编号等）不猜测（需求2.2第6条）；子Agent的证据冲突时停止写入并问人（需求6.2规则4）。这和「作判断」不同：判断可以由Agent作出，事实不能编造。
  4. 审核卡增加「过程中作出的判断」。 放在「需要你做什么」之后，每条写明：事项、Agent的选择、考虑过的备选、理由、依据（链接到原文）、风险高低。结构化结果（需求6.4、技术方案4.8）增加对应的字段 decisions[]。审核卡由七部分变为八部分。
  5. 取消「高风险先写判断」的强制要求（需求2.4末段、3.4规则3、6.8第1条；技术方案3.3；执行方案PR-16、PR-27）。防过度依赖的措施保留植入缺陷的检出率统计和审核卡上的「不确定事项」。
  6. 等级（需求2.3）：首版所有能力的最终结果都交人审核（相当于等级2）；等级3（抽查后直接生效）以后按评测和试用数据开放。需求2.4规则5（内部请求在等级3且注册人员同意后免逐次批准）由权限模式取代。
  7. 「请求批准模式下关键判断先问」是Agent的工作方法，由系统提示词和技能规定，系统无法逐条识别「判断」；兜底是最终审核卡逐条列出所有判断。

1.5 Agent在对话中汇报进度

  1. Agent开始一项工作时列出步骤（计划与待办），每完成一步在对话中用一句话说明做到了哪一步、下一步做什么。
  2. 运行中，输入框上方显示当前状态：正在做什么、第几步共几步、已用时间，以及停止按钮；计划可以展开查看。
  3. 后台运行（人不在线时）同样把进度写进对话。只有需要人处理的事（批准请求、提问、阻塞）和最终结果才推送通知，其余按需求3.8「少打扰」合并进日摘要。

1.6 界面：简洁，参考Codex、Claude Code、DSH

界面以对话为中心，视觉上安静、克制。具体要求见附录A，它替代技术方案3.1–3.3中与之冲突的布局和样式描述。现有界面稿（PR-03）按附录A重做后，再开发正式界面（PR-26、PR-27）。

附录A 界面风格要求

参考Codex、Claude Code和DSH的界面：以对话为中心，安静、克制，信息按需出现。只参考它们的布局和交互方式，不复制它们的标志、图标、配色和代码。

A.1 方向

  • 用户是注册人员，在办公室用桌面浏览器长时间工作。主要做三件事：交代工作、看进度、审核结果。
  • 整体像一份干净的工作文档：白底、黑灰文字、细分隔线，几乎没有装饰。
  • 只让一处被记住：依据。结论中的引用可以一键打开原文和原页并排对照，这是本产品区别于一般聊天工具的地方。其他元素都保持安静。
  • 强调色只用于「需要你处理」：批准请求、待审核、主要按钮和焦点。

A.2 颜色

名称色值用途
纸#FFFFFF对话区和右栏的背景
侧栏#F5F6F7左栏背景、人的消息的底色
墨#1C1F23正文
灰#5F6670次要文字、工具步骤
线#E4E6E9分隔线、输入框边框
墨蓝#2A4D8F强调色：主要按钮、批准请求、焦点、待处理数量

状态色只用于检查结果和运行状态，饱和度较低：通过 #2F7D4F，注意 #A86A00，失败 #B42318。首版只做浅色主题；颜色写成设计变量，以后可以加深色主题。

A.3 文字

  • 用系统字体，不引用网络字体："PingFang SC", "Microsoft YaHei UI", "Microsoft YaHei", "Segoe UI", system-ui, sans-serif。
  • 等宽字体只用于标识符和路径（K号、文件名、版本号、代码）："Cascadia Mono", Consolas, "SF Mono", monospace；不用于装饰性的小标签。
  • 字号：正文15px，行高1.75；控件14px；次要信息13px；项目标题18px。只有项目标题和审核卡的结论用600字重，其余用400。
  • 用平实的动词。按钮写清点了会发生什么（「通过」「退回修改」「允许」「拒绝」），按钮文字后不加箭头；错误信息写清发生了什么、怎么处理。

  • 右栏（约520px）：只在审核、看改动、看原文时从右侧打开，可以关闭，不常驻。

A.6 输入框

  • 底部的圆角输入框，多行；回车发送，Shift加回车换行；运行中「发送」变为「停止」，运行中输入的话作为插话。
  • 左下角依次是：附件；Agent选择（只在新对话中可以选，项目中的对话显示当前Agent）；权限模式选择（只读、请求批准、完全允许，每项附一句说明）。
  • 占位文字随Agent变化，例如「让注册Agent做什么？」。

A.7 审核

  • 右栏中按八部分排列：结论（较大字号）、需要你做什么、过程中作出的判断、改动、依据、自检、不确定事项，底部固定操作按钮。各部分用普通的小标题，不加编号。
  • 主要按钮「通过」，次要按钮「退回修改」；「修改后通过」「追问」「转交他人」放在更多操作里。
  • 显示所针对的工作区版本；版本已变化时提示刷新。

A.8 不要做的

  • 不用编号标记（01、02……），除非内容本身是顺序步骤（计划的步骤可以编号）。
  • 标题上方不加眉题式的小标签；不用「A · B · C」式的元信息串；按钮文字后不加箭头。
  • 不用深色侧栏、渐变、大面积色块和装饰插图；不把内容切成一张张带阴影的卡片，卡片里不再套卡片。
  • 徽章只用于需要人处理的数量和检查结果，不到处贴状态标签。
  • 正式界面中不出现「界面稿」「示例数据」之类的标记；开发环境可以在设置中显示一行小字。
  • 不做与操作无关的动画。只保留展开、收起、打开右栏这类由人触发的过渡（150–200毫秒），并遵守系统的「减少动态效果」设置。

A.9 质量底线

  • 主要操作可以用键盘完成：Ctrl加K搜索，Esc关闭右栏；焦点可见（2px强调色）。
  • 文字与背景的对比度符合WCAG AA。
  • 以1280px以上的桌面为主；窄于1024px时左栏自动收起。手机端按D16另行决定。
  • 图标用统一的线性图标（16px），随前端打包，不从外部加载。
