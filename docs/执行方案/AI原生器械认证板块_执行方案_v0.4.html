1.2 分支、提交与PR

  • 每个PR一个分支，从最新的 main 建立，命名为 pr-NN-<英文短名>，例如 pr-07-workspace。
  • 提交信息用中文，以PR编号开头，例如「PR-07 项目工作区：保存与冲突检测」。
  • 用 gh pr create 开PR，按仓库中的PR模板填写：做了什么、没做什么、验收结果、对应的需求和技术方案章节、真实模型测试的费用、新增依赖、风险和需要Lan决定的事。
  • PR开出后，先做一次AI代码审查（Codex的审查功能，或Cursor的Bugbot），处理审查意见后再进入合并；Lan重点看动作级别、审批、沙箱、数据级别、密钥等关键部分。
  • 不直接推送到 main，不改写已推送的历史，不强推。
  • 自行合并的授权（2026-11-17晚，Lan）：在主路径走通之前，Codex可以在该PR的检查通过、自查（含上面的AI代码审查；有GitHub持续集成时还要等它通过）之后自行合并。授权持续到主路径走通，也就是PR-C4、PR-21、PR-25、PR-26、PR-27完成。Lan事后补审；审出的问题用后续PR修改，不改写已经合并的历史。主路径走通后，恢复为由Lan审查并合并。
  • GitHub仓库设置：main 应经PR合并且持续集成通过，禁止强制推送。2026-11-17设置分支保护时，GitHub返回403，当前套餐不能启用。仓库保持私有。保护启用之前，靠上面的流程约束。是否升级套餐由Lan决定。

1.3 每个PR的通用验收

除各PR自己的验收外，每个PR都要满足：

  1. pnpm lint、pnpm typecheck、pnpm test 全部通过；涉及数据库的PR，pnpm dev:up 后 pnpm test:int 通过；涉及Python服务的PR，pnpm test:py 通过。
  2. 持续集成通过，其中包括密钥扫描（gitleaks）。
  3. 新增或改变的行为都有测试；修复缺陷时先写能复现的测试。
  4. 设计有变化时，同步修改 docs/ 中的文档，并运行 pnpm docs:html 生成HTML。
  5. 新增依赖在PR说明中写明版本、许可证、是否默认向外发送数据（前端依赖尤其要查统计和错误上报）。
  6. 从参考项目移植的文件，文件头注明来源路径并保留MIT版权声明。
  7. 用到Pi的接口时，在PR说明中写明实际行为是否与技术方案的预期一致。

1.5 什么时候停下来问Lan

  • 需求、总体方案、技术方案、数据与评测方案和本文之间有冲突，或范围不清楚；
  • 需要偏离技术方案的设计，包括更换技术选型；
  • 本PR必须对标为待定的事项作出选择（技术方案第13章、需求第10章、本文第8章）；
  • Pi的接口与预期不符，影响设计；
  • 界面需要偏离已确认的界面稿；
  • 需要新增出网地址、外部服务或密钥；
  • 需要放宽任何安全约束：沙箱隔离、业务工具的授权、审批来源、数据级别路由、出网白名单、界面不加载外部资源；
  • 一个PR的真实模型测试费用预计超过10美元；
  • 同一个问题尝试三次仍未解决。

提问时说明卡在哪里、有哪几种做法、建议哪一种以及理由。
