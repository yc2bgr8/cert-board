1 开发方式

1.1 分工

角色做什么
Codex一次做一个PR：按本文的条目实现、写测试、跑验收、开PR、按审查意见修改；起草技能和其他内容任务。遇到1.5中的情况时停下来问
Lan审查和合并PR；回答Codex的问题；在需要时运行真实模型测试；协调注册人员完成内容任务和界面稿确认；决定待定事项
注册人员A、B确认界面稿；审阅技能和其他内容任务的结果（第5章）；切片试用；第一期各能力的验收

1.2 分支、提交与PR

  • 每个PR一个分支，从最新的 main 建立，命名为 pr-NN-<英文短名>，例如 pr-07-workspace。
  • 提交信息用中文，以PR编号开头，例如「PR-07 项目工作区：保存与冲突检测」。
  • 用 gh pr create 开PR，按仓库中的PR模板填写：做了什么、没做什么、验收结果、对应的需求和技术方案章节、真实模型测试的费用、新增依赖、风险和需要Lan决定的事。
  • PR开出后，先做一次AI代码审查（Codex的审查功能，或Cursor的Bugbot），处理审查意见后再请Lan审查；Lan重点看动作级别、审批、沙箱、数据级别、密钥等关键部分。
  • Codex不合并PR，不直接推送到 main，不改写已推送的历史。
  • GitHub仓库设置：main 分支受保护，必须经PR合并且持续集成通过，禁止强制推送。

1.3 每个PR的通用验收

除各PR自己的验收外，每个PR都要满足：

  1. pnpm lint、pnpm typecheck、pnpm test 全部通过；涉及数据库的PR，pnpm dev:up 后 pnpm test:int 通过；涉及Python服务的PR，pnpm test:py 通过。
  2. 持续集成通过，其中包括密钥扫描（gitleaks）。
  3. 新增或改变的行为都有测试；修复缺陷时先写能复现的测试。
  4. 设计有变化时，同步修改 docs/ 中的文档，并运行 pnpm docs:html 生成HTML。
  5. 新增依赖在PR说明中写明版本、许可证、是否默认向外发送数据（前端依赖尤其要查统计和错误上报）。
  6. 从参考项目移植的文件，文件头注明来源路径并保留MIT版权声明。
  7. 用到Pi的接口时，在PR说明中写明实际行为是否与技术方案的预期一致。

1.4 测试的分层和运行条件

层次命令运行条件是否在持续集成中运行
单元测试pnpm test无是
集成测试pnpm test:int本地依赖服务已启动（pnpm dev:up）是，持续集成中用服务容器
Python服务测试pnpm test:py在服务的容器中运行是
Agent测试pnpm eval:agentAgent内核以无界面方式运行，用剧本模型是（PR-29之后）
真实模型测试pnpm test:real.env.local 中有 OPENROUTER_API_KEY；没有时跳过否，本地运行，费用写入PR说明
L08测试pnpm test:l08环境变量 CERT_DATA_DIR 指向参考资料快照的数据目录；没有时跳过否
端到端测试pnpm test:e2e完整环境已启动否，切片后期按需加入
评测pnpm eval剧本模型部分无条件；真实模型部分同上剧本模型部分是

不能为了让测试通过而放宽检查、跳过测试或修改期望值。确实需要修改期望值时，在PR说明中逐条解释。

1.5 什么时候停下来问Lan

  • 需求、技术方案、本文之间有冲突，或范围不清楚；
  • 需要偏离技术方案的设计，包括更换技术选型；
  • 本PR必须对标为待定的事项作出选择（技术方案第13章、需求第10章、本文第8章）；
  • Pi的接口与预期不符，影响设计；
  • 界面需要偏离已确认的界面稿；
  • 需要新增出网地址、外部服务或密钥；
  • 需要放宽任何安全约束：沙箱隔离、业务工具的授权、审批来源、数据级别路由、出网白名单、界面不加载外部资源；
  • 一个PR的真实模型测试费用预计超过10美元；
  • 同一个问题尝试三次仍未解决。

提问时说明卡在哪里、有哪几种做法、建议哪一种以及理由。

1.6 开发环境

  • 本机已有：Windows；Node 24.22；Git；WSL（Ubuntu-24.04）中的Docker 29和Compose。
  • 需要安装：pnpm（npm install -g pnpm@9）；GitHub CLI（winget install GitHub.cli，然后 gh auth login）。gitleaks在持续集成中运行，本机可选；Python服务的测试在容器中运行，本机不需要装Python。
