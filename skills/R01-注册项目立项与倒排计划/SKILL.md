# R01 注册项目立项与倒排计划

草稿，待注册人员确认。依据需求 V1.0 的 R01、P01、P02，SY-QP-15 A3 第 5.1、5.2、5.4、5.5、5.7 节，以及 E23 的历史节点回填口径。

## 启动条件

注册人员提出新项目、要核算交付目标日期、希望修订计划或回填已有项目节点时使用。在项目里先用 `cert_context` 读取当前方向。收集产品、型号、市场、拟定路径、目标日期及可确认的负责人。目标日期缺失时向发起人询问；路径未决定时留待 R02。当前工具目录无法创建项目时，回报缺口，请在项目页创建后继续。依据《新产品开发项目建议书》《设计开发进度计划》和《设计策划评审记录》。

## 规划和回填

1. 用 `doc_search` 定位，用 `doc_read` 取得产品定义、项目计划、测试报告、收件回执和变更原文。先区分目标、候选日期、实际事件、签署和决定日期。历史日期与前后步骤的关系不足以证明发生，不从报告发布日期推算试验或送样日期。依据 SY-QP-15 A3 第 5.1、5.4、5.5 节。
2. 按已经确认的市场和路径选择节点，检查测试、样品、合同、付款、草稿报告、终稿、拟提交、受理、发补、回复、批准和续期哪些适用。内部准备和样品试制按项目自有资料核对。为每个计划节点记录已知负责人、日历日工期、前置节点和工期出处或待确认状态。实际事件单列原文出处，缺失实际日期的节点标「缺少证据」。依据需求 R01 和《设计开发进度计划》。
3. 准备好完整工期与前置关系后用 `work_schedule_calculate` 计算倒排、关键路径和最晚开始日。需要法域期限的节点用 `deadline_calc` 计算并单独引用。若最早开始条件与目标冲突，解释限制和影响，列可选方案，等待注册人员决定目标日期。计划节点调整时保留上版计划、改变的负责人或日期及理由。依据需求 R01、D20 和技术方案的时间约定。
4. 每完成一步在对话汇报已经核对的资料和下一步。关键判断先按当前权限模式处理。只读模式只答复；请求批准模式在关键判断前提出建议和出处并等人确认。项目最终计划用审核卡交注册人员。

## 交付和审核

工作副本中保存 `交付/注册计划.md`。按节点展示计划日期、负责人、依赖、实际事件与引用、关键路径和风险。涉及历史回填时分开列实际事件和待核项。未看到立项、送样、付款、草稿报告原文时分别列缺少证据。公司正式记录、签署、监管提交和缴费由人按现行工作流程完成。

保存后按 `check_run` 和 `submit_for_review` 交审核卡，保持 `workspaceVersion` 对应当前版本。原文逐字引用，所引出处保留资料号、版本和页码。实际日期未获得有效证据的节点继续保持未证实。
