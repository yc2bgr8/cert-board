# R09 一致性检查

草稿，待注册人员确认。所属Agent：registration。仅供开发环境测试，不可作为生产发布版本。

## 适用范围

核对申报包各资料版本，列出可核查的差异、缺件和交人判断事项。按用户给出的范围执行。用户只问一个编号或一个字段时，核对该项及必要上下文。用户要求整包检查时，按下文五组取证。处理差异的建议属于过程判断，按当前权限模式进行并交人审核。

## 工作方法

阅读后端随对话提供的项目 AGENTS.md 与本技能。工具目录提供 plan_update 时列出取证、写稿保存、检查送审。只读时直接按取证、复判、答复推进。每完成一步，用一句话汇报已经读到什么、下一步是什么。新核查直接查看资料库，旧核查稿只在用户要求修改或比较该稿时读取。搜索摘要、工作区草稿和模型记忆不能充当原文证据。依据 AGENTS.md 的系统提示词工作方法及 v6 第 1.3 节。

## 整包核查

1. 读取项目资料和申报清单，记录本轮的资料版本及未解析的资料。用 rules_run 运行 R0–R7，同一批按回执的 nextOffset 继续，并保留同一资料版本清单。候选可重复或来自不同用途，须逐条复判。R5 的 xfa_datasets 定位供人核对 eSTAR 原件，缺件须对照真实附件清单。清单或原件不齐时标为待确认。依据 SY-QP-15 A3 第 5.3、5.7 节、《设计开发输出清单》和《设计开发转换清单》。
2. 资料较多且当前模式提供 subagent_run 时，按下表分组委派。只读模式由当前 Agent 按同样五组直接读取。任务只取证及整理候选，当前 Agent 合并重复结果并处理证据冲突。各组保留原文、资料 UUID、版本、页码、字段值、单位和所在试验或文件用途。任何一组找不到证据时，把缺口写入交付。按项目内实际资料分组，单项查询按实际需要取证。依据需求 R09、6.2、6.4 和技术方案 8.2。
3. 对照同一型号、同一条件和同一字段。区分实际差异、术语或单位等价、试验条件或用途不同。塑形后冷却的水温与清洁冲洗水温分别比较，试剂与产品储存条件分别比较。实验室结论栏为斜线需结合接受标准解释，接触时长类别和使用期限均列原文，累计接触评估交人判断。依据 RV-05 第 6 章与 SY-QP-15 A3 第 5.5、5.6 节及《设计验证记录》。
4. 每条待送审差异须有两处实际读到的独立原文定位。父 Agent 对所有送审引文核对 doc_read 回执。只找到一处或只找到占位页时，列为待核证据而非已核实差异。报告逐条写明发现层、复判理由、处理建议和待确认事项。依据需求 6.5、6.6 和技术方案 8.2。

| 组 | 核对字段 |
|---|---|
| 申报信函与摘要 | 申请人、联系人、申报路径、对比器械 K 号、声明和封面版本 |
| 器械描述与标签 | 型号、配置、材料色母、预期用途及人群、关键参数、使用与储存期限、说明书和包装 |
| 测试报告 | 报告号、日期、版本、标准版次、试验条件、数值与单位、接受标准及结论 |
| 材料与 MSDS | 材料、部件和型号对应、色母、材料报告和安全资料引用 |
| eSTAR 表单与附件 | 表单与实际附件清单、内嵌及外层版本、引用位置及待核缺件 |

公开标识符需要核实时，用 official_lookup 查询已公开的编号，并用 identifier_check 核对材料与可引用的官方或可信台账原文。未取得有效证据时保留两份材料原文及待确认项。数值陈述保留其场景、源单位和逐字引用，按 check_run 的 quantityCheck 格式交程序复算。缺接受标准时标为待评价。默认规则命中只是候选，包括 R2、R4 的混排版式应回到原件核对。

## 单项核查

doc_search 是大小写不敏感的原样子串检索。英文申报包优先查看 510(k) 摘要中的对比器械字段，检索 510(k) number 或 predicate device，首次取少量结果。选出相关的两三个位置，可在同一轮发起这些 doc_read 调用。根据返回的资料名、UUID、版本、页码和 snippetOffset 读取。不从全文广搜单字 K 或遍历全部命中。证据不足时，用更具体短语、摘要名称或已经实际读到的编号补查。依据 FDA《Content of a 510(k)》的对比器械识别部分，以及 SY-QP-15 A3 第 5.3 节和《设计开发输出清单》的资料定位字段。

doc_read 的 id 必须来自检索结果的 documentId，不能把资料编号当作UUID。优先将命中项的 snippetOffset 作为 offset，从命中附近读取默认1800个UTF-16字符；这与检索结果的分页 offset 不同。仅在引语或判断所需相邻上下文不完整时追加小片段，必要时调整 offset/limit 重读覆盖完整引语的一段，不拼接缺口或改写原文。不要自动沿 nextOffset 读完整页，也不要重复读已经覆盖的整页。记录前后两处原始写法及它们的来源，不从搜索摘要直接写结论。依据工具目录的 doc_read 说明、SY-QP-15 A3 第 5.3 节和本项目实际文件版本。

实际读到两处不同写法、各有完整可核验引语及足够相邻上下文后，就准备候选差异报告并进入自查和审核；仅为解除具体不确定性再补查。报告写明本次读取范围，不声称已穷尽整包；如果仍无法判断哪个编号正确，保留两种原文并列为待确认，不用更多重复检索代替人的确认。

将不同写法分别记录为带资料编号、版本、页码和逐字摘录的陈述。Word 页码是抽取单元，不冒称纸面页码；OCR 低置信内容和原始 PDF 占位页须明确说明限制。两条证据可以来自同一页的不同完整引语；仅改变空白重复同一引语不增加证据数。

有依据的过程判断写入 decisions。如果现有证据只证明写法不同，就保留差异，把正确编号列为待确认。确需作出「按笔误处理」等关键判断时，请求批准模式先提出建议、备选、理由和原文，用 ask_user 等待确认，完全允许模式下作出有依据的判断再继续。业务工具要求批准时，等 pending_approval 对应的浏览器决定。被拒绝后按原因调整。依据需求 V1.0 的最终结果审核与权限模式规则，以及 FDA 的对比器械识别指引。

## 保存、修改与送审

用 ws_write 在工作副本新建 `交付/一致性检查结果.md`，写清原文定位、差异及待确认事项。若用户提供明确的交付路径则按该路径。修改已有稿件时先读最新版本，把每条修改意见与对应部分对照，只改指定部分及其必需的相邻说明。新文件可省略 expectedSha256，修改既有文件时使用读取回执的版本和哈希。用工具回执的 draft.version 作为 workspace_save 的 expectedDraftVersion 保存工作区。取保存回执的 workspaceVersion，运行 check_run，再用 submit_for_review。每条引语须完整出现在本对话的 doc_read 回执中。依据 AGENTS.md 的工作区版本规则、需求第 3.3 节和技术方案 8.2。

只读模式按规则读取和回答，保留候选、原文和缺口。请求批准模式在实际业务工具要求时等浏览器批准，关键过程判断先给建议和证据再请人确认。最终结果照常走浏览器审核。资料缺失不补造，已提交的原件保持原样。

## 交付与审核

交付工作区中的核查报告及结构化结果，包含 `skill`、`workspaceVersion`、`conclusion`、`claims`、`evidence`、`decisions`、`missing`、`uncertain` 和 `nextStep`。每项过程判断列明事项、选择、备选、理由、出处和风险，判断中的原文同样须经过 `doc_read` 和 V1 检查。没有过程判断时传 `decisions: []`。K 号用字符串，单位传 `null`。同一数值陈述附它的数字和单位原文，另一个来源如有不同数值则分别列条。V2 写出实际所用回执和没查到的字段。只按实际检查结果写状态。

提交后等待浏览器审核卡的决定；对话中的“已批准”无效。通过只冻结本报告版本，不代表正确 K 号已获确认，也不代表已向监管机构提交。
